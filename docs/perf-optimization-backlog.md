## 音视频渲染

### A1｜纯音频 diff 走 remux，跳过视频重编码 —— P1｜未动工

- **证据**：组 1 t4「换个BGM」轮 64.9s 中 `exec_render` 17.7s，而视频轨内容零变化
  （audio 块换曲 + fade）；同类修订轮（改字幕/旁白/音量）都存在同样的全片重编码浪费。
  对照组：组 2 t2「换个BGM」渲染仅 12.9s（素材更短）——纯音频修订轮的渲染占比
  40~50%，且与视频内容无关。
- **方向**：修订轮 `plan_diff` 判定「音频-only diff」（`audio` 块变化且 clips/timeline/
  overlays 未变）→ 渲染命令降级为两段式：复用上一版的视频段 concat（或直接复用上一版
  产物轨），仅对新音频块跑滤镜 + `-c:v copy` remux。
- **预期**：该类修订轮渲染 17.7s → ~2-3s（remux 级）；修订轮总耗时下限逼近
  「LLM 往返 + 音频处理」。
- **边界**：转场/效果涉及视频时必须回退全编码；verify 口径不变（时长校验照跑）。

### A2｜感知层并发上限（ANALYZE_PARALLELISM=2）—— **已落地**（2026-11-01）

- **根因（两轮修正后定论）**：agent 一轮并行调 6 个 analyze_media，解码 + TransNet
  推理 + VLM 上传互相争抢（span 实测 6 路同时启动）。信号量限到 2 后该文件
  analyze 229.9 → 169.9s。⚠️ 首轮「瓶颈从来不是解码」的判断源于合成素材基准
  （555fps），**真实微信素材单遍软解本体就要 ~47s（2.5K HEVC10）/~20s（4K H.264）**，
  解码本身就是感知层大头之一 → 解码本身的优化归 A3。
- **落地**：`content_analysis` 模块级信号量 `ANALYZE_PARALLELISM`（默认 2）包住
  analyze_media 重管线；span 记 `waited_sem_s`。总墙钟反而更短（串行求和 <
  争抢放大的并行），VLM 请求密度同步下降。

### A3｜HEVC 素材感知层解码走硬件加速 —— P1｜**已落地**（2026-11-03）

- **证据（2026-11-03 真实素材基准，翻案 A2 首轮否决）**：2.5K HEVC Main10（微信
  导出全此规格）单遍解码软解 47.4s vs d3d11va **19.6s（2.4×）**；4K H.264 相反
  （软解 19.8s vs 硬解 27.2s）——**必须按 codec 条件启用**，`-hwaccel auto` 会
  在 H.264 上误抓硬解反而变慢（29.2s），不能无脑加。
- **落地**：`analyze_media` 按 probe 的 `codec == "hevc"` 给两遍全解命令
  （detect_av 信号检测 + TransNet 管道 + 切分阶梯兜底）插入 `-hwaccel d3d11va`
  （初始化失败自动回退软解，无 GPU 机器零行为变化）。H.264/其他编码保持软解。
  开关 `HEVC_HWACCEL=0` 关闭。
- **回测（2026-11-03）**：真实 2.5K HEVC10 素材完整 analyze（冷卡片、单文件）：
  **218.0s → 94.4s（-57%）**；两遍全解 91.7+85.2s → 31.6+24.0s（3.2×）。
  组2 创建轮预计再省 ~120s（该文件 analyze 169.9 → ~95s）。

## VLM 感知层

### V1｜GLM-4.5V 打标关闭 thinking（enable_thinking:false）—— P0｜**已落地**（2026-11-01）

- **证据**：冷启动单请求 input 2166 → **output 63,370 tokens（961s）**，批次 978s 失败；
  **当晚数据集重放二次独立复现**（同一 6 帧批次 716s、`n_chunks=63,371`，signature
  完全一致）——素材重上传使缓存键失效即必触发。
- **落地**：`model.get_vlm_model` 的 extra_body 加 `enable_thinking: VLM_THINKING`
  （默认 False，`VLM_THINKING=1` 可开回对照）。真机冒烟：6 帧请求
  `reasoning: 0`、output 212 tokens（对比失控批次 63k）。
- **回测（2026-11-02）**：组3 创建轮 1463.3 → **394.2s（-73%）**；曾烧 716s/63,371 chunks
  的 63a156 素材 4 批全成功（6.6~10.0s/批），零 429 零失败批。超预期落地。

### V2｜预热与任务内共享在途分析（双路挤兑去重）—— P0｜**已落地**（2026-11-01）

- **证据**：63a156 素材预热跑 1011s 未落盘，任务内 `analyze_media` 又完整重算 1457s。
- **落地**：`content_analysis` 模块级在途注册表（按绝对路径），后来者等先到者收尾后
  重入——成功则命中缓存、失败则自己重算（失败不传染）；超时兜底
  `INFLIGHT_ANALYZE_TIMEOUT`（默认 1500s）。span 记 `waited_inflight_s`。
- **回测**：单测 test_v2_inflight_dedup_same_file（并发只跑一遍管线）通过；重放全程零 error span、无 429（基线组3 有 2 个失败批）。

### V3｜打标并发 4→2 —— P1｜**已落地**（2026-11-01）

- **证据**：预热 4 路 + 任务内 4 路 = 8 路 `OpenAIRateLimitError` 实录 ×2。
- **落地**：`VLM_CONCURRENCY` 默认 2（可显式调回）；配合 A2 的感知层并发上限，
  VLM 请求密度整体受控。
- **回测**：单测 test_v3_tag_shots_default_two_workers 通过；重放全程零 error span、无 429（基线组3 有 2 个失败批）。

### V4｜TransNetV2 CPU 推理热点 —— P2｜未动工

- **证据**：组 1 t0 三个短视频的 `analyze_media` 各有 ~15s 独占时间（非 LLM/VLM/ffmpeg）
  = TransNet CPU 推理；冷路径专属，卡片缓存后消失。
- **方向**：短片（<15s）跳过模型直接 ffmpeg 启发式，或 GPU/批量推理。

## LLM 请求与上下文

### L1｜阶段 2 上下文瘦身 —— P0｜未动工（已有立项）

- **证据**：大工具轮 prompt 2.7万~4.7万字符、单笔 20~30s；修订轮逐轮膨胀
  （28k→33k）；失败轮单笔 292s。
- **方向**：素材卡片摘要化进 brief、消息构造瘦身、生成预算封顶。

### L2｜一键成片宏的 LLM 次数合并 —— P1｜未动工

- **证据**：热稳态创建轮 24 次/244s（旁白、逐镜文案、BGM 挑选串行藏在 compile_expand）。
- **方向**：旁白+文案合并一次出；文案类换更快的小模型；无依赖调用并行。

### L3｜TTFT 尖刺的观测与兜底 —— P2｜未动工

- **证据**：16 轮样本至少 2 次大尖刺——组 1 t4 单笔 19.3s（1.4 万 token 预填充，基线应
  <2s，一轮被吃掉 30%）；组 1 t1 单笔 22.8s（prompt 仅 6k 字符，纯排队）。同轮其余调用
  0.4~2.6s——供应商排队抖动/前缀缓存未命中，与请求大小无关。
- **方向**：先靠埋点观察发生率；若高频，考虑 TTFT 超阈值（如 >8s）断开重发的兜底杠杆。

### L5｜主模型关闭 thinking（enable_thinking:false）—— P0｜**已落地**（2026-11-03）

- **证据（怎么看出开着思考的）**：埋点 llm span 的 `meta.usage.output_token_details
  .reasoning`——后测 128 笔主模型调用里 **70 笔带 reasoning，合计 28,220 tok（占
  输出 34% ≈ 310s）**；典型签名：一笔 27.8s 调用 out=3066、reasoning=2851、正文
  仅 415 字符（思考不进正文但时间照烧）。TTFT 仅占 15%（均 1.2s），慢的全在生成。
- **真机探针（末块 usage 口径）**：默认开（reasoning=467）；`enable_thinking=false`
  有效（reasoning=0，同题快 34%）；`thinking_budget=256` 被遵守（reasoning=252）。
- **落地**：`model.get_model` SiliconFlow 路径 extra_body 加
  `enable_thinking: MODEL_THINKING`（默认 False，`MODEL_THINKING=1` 开回对照；
  通用 OpenAI 路径不带——非标参数）。生产路径复测 reasoning=0、正文正常。
- **预期/回测**：按 34% 占比，三组 LLM 生成 ~903s → ~600s；**待数据集重放确认
  耗时与成片质量**（关思考后计划质量是否受损是唯一风险点；budget 封顶方案已
  验证可用，质量降级时的备胎）。

### L4｜结构性修订触发旁白/文案全量重生成 —— P1｜未动工

- **证据**：组 1 t1「时长改为50s」15 笔 LLM/252.5s，其中 **~5 笔 ×15~24s（约 90s）是
  旁白+逐镜文案对全部镜头的重新生成**（prompt 6~8k、输出 1.5~2.4k 字符的画像）——
  时长变化只影响部分镜头，未受影响镜头的文案被一并重写。对照组：组 2 t1「去掉字幕」
  （纯删除、无重生成）仅 6 笔/27.9s。
- **方向**：diff 出受影响镜头集合，旁白/文案只对增量镜头重生成，其余复用；顺带评估
  与 L2 的合并 prompt 是否冲突（增量重生成会打破一次性全文输出的前提）。
