## 一、背景与定位

V3.1 之前的 `probe_media` 只读 ffprobe 容器头（时长/分辨率/编码/有无音轨），
从不解码内容——「帮我剪和朋友一起的时光」「只留有人的画面」「挑最精彩的三段」
这类**语义筛选任务在系统中无法表达**，模型只能瞎猜时间戳（而编造的时间戳恰好
能通过全部现有校验，是最危险的一类幻觉）。

**V4 补上感知层**：每个素材可建立一个「内容卡片」——镜头级时间区间 + 语义标签
（人数/场景/活动/情绪/画质），由新增的 `analyze_media` 工具按需生成、sidecar 缓存。
规划模型读到卡片后**手写显式 trim** 完成筛选——计划 schema、编译器、渲染链路
**零改动**，"LLM 出意图，编译器保正确"的分工不变。

## 二、架构总览

```
工作流（V2_SYSTEM_PROMPT）
  1. ls INPUT/
  2. probe_media(path)              # 容器元数据：必做、便宜、零改动
  3. 任务涉及内容理解？→ analyze_media(path)      # 新增（V4）
       ├─ sidecar 命中（TMP/probe/<hash>.json）→ 直接返回卡片
       ├─ ① 场景切分：ffmpeg select='eq(n,0)+gt(scene,0.3)' + showinfo
       │      → 镜头边界；超 24 帧预算均匀下采样；>12s 长镜头等分加密
       ├─ ② 抽代表帧：每镜头 0.35 分位处，长边 640px JPEG → base64
       └─ ③ VLM 批量打标：6 帧/批，严格 JSON，只出标签不报时间
  4. 可行性自检 → 5. submit_plan（模型读卡片挑区间，写显式 trim）→ 6. ask_user
  ⇒ 之后全链复用：Tier 2 校验 → 编译 → 渲染 → 回验
```

| 模块 | 职责 |
|---|---|
| `video_editing/content_analysis.py`（新增） | 感知层全部：场景切分/抽帧/打标/卡片/sidecar/进度钩子 |
| `model.py` | +`get_vlm_model()`：VLM 客户端，独立于规划模型，无 key 返回 None |
| `video_editing/video_agent.py` | +`analyze_media` 工具；工作流提示词插入内容理解步骤与防幻觉硬规则 |
| `web/server.py` | 感知进度 → NDJSON `analysis` 事件；`/api/inputs?probe=1` 附带缓存卡片 |
| `web/index.html` | 右栏新「内容索引 · 镜头卡」：进度条 + 镜头表（区间/人数/场景/活动/画质） |
| `tests/test_content_analysis.py`（新增） | 19 项离线单测（全 mock，不联网） |

## 三、设计决策（实现定稿）

### D1 · 时间与语义分工：时间来自确定性信号，VLM 只出标签

镜头边界全部由 ffmpeg 场景检测产生；VLM 提示词明令禁止输出时间戳，打标结果
只按帧序号对位到镜头。**从结构上杜绝「VLM 幻觉时间戳且能通过全部校验」**
（dev-notes D5 点名的语义幻觉实例）。e2e 中模型的 `trim_start: 8.767` 正是
卡片给出的镜头边界——模型引用信号而非编造。

### D2 · 独立工具 `analyze_media`（2026-09-24 评审修订）

原方案内嵌 `probe_media`（探测即索引）；评审改为**独立工具**：纯机械任务
（截取/拼接/加字幕）不必付 VLM 的 token，由模型判断任务是否涉及内容理解、
按需调用。配套三道防护（对应 plan §4.5）：

1. **提示词硬规则**：内容类任务必须先 `analyze_media` 再动笔；没有卡片不得
   凭空写语义 trim，宁可 `ask_user`；
2. **标签 schema 固定、与任务无关**：卡片字段不按用户问题定制——否则缓存从
   按文件失效退化成按问题失效，"复用零重算"崩塌（`sanitize_label` 强制收敛）；
3. **跳过率是观察项**：实测中未出现漏调；若日后不可忽略，仿 `_l1_scan` 加
   warn 级扫描（多段细粒度 trim + 从未调用 analyze_media）。

### D3 · 缓存：sidecar `TMP/probe/<hash>.json`（即 roadmap T11）

键 = `文件名|大小|mtime`（与 web `_probe_file` 同策略），文件变动自动失效。
实测第二次分析 **0.001s 命中**。卡片含 `cached` 标记，`/api/inputs?probe=1`
顺带返回（零成本）。

### D4 · 四级降级，链路永不因感知失败而断

| 级别 | 触发 | 行为 |
|---|---|---|
| `vlm_unavailable` | 无任何 VLM key | 只返回场景切分（L1 信号），卡片照常可用 |
| `uniform_fallback` | 场景检测失败/无切点 | 按时长每 ~5s 均匀切分兜底 |
| `tag_partial` | 某批打标两次失败 | 该批镜头标 `tag_failed`，其余照常 |
| `{"error": ...}` | 文件不存在/纯音频/抽帧全败 | 结构化错误返回给模型（可走 ask_user） |

### D5 · 成本钉死在分级

帧预算 `VLM_FRAME_BUDGET`（默认 24）× 长边 640px JPEG × 6 帧/批。单文件首次
分析 ≈ 25–50k 输入 token（按 GLM-4.5V ¥1/M 进 / ¥6/M 出 ≈ **4–6 分钱**），
之后缓存为零。

## 四、配置（.env，全部可选）

| 变量 | 默认 | 说明 |
|---|---|---|
| `VLM_MODEL` | `zai-org/GLM-4.5V` | 打标模型；备选 `Qwen/Qwen3-VL-30B-A3B-Instruct`（更快更省） |
| `VLM_API_KEY` | 回退 `SILICONFLOW_API_KEY` | 独立供应商 key（配它就不再复用 SiliconFlow） |
| `VLM_BASE_URL` | SiliconFlow 端点 | 独立供应商必须显式给 OpenAI 兼容端点 |
| `VLM_FRAME_BUDGET` | 24 | 每素材抽帧上限（成本闸） |
| `VLM_BATCH` | 6 | 每次请求带几帧 |

不配任何 VLM 变量 → 自动复用 SiliconFlow key（零配置可用）；两边都无 key →
降级为纯场景切分信号，全链路照常。

## 五、内容卡片 schema（v1）

```json
{
  "schema_version": 1, "source": "INPUT/x.mp4", "vlm_model": "zai-org/GLM-4.5V",
  "duration": 17.533, "frame_budget": 24, "degradations": [],
  "summary": "共 2 个镜头/17.533s；场景：户外×2；活动：表演×2；多人镜头 2 个",
  "shots": [
    {"start": 0.0, "end": 8.767,
     "label": {"person_count": 5, "has_children": false, "scene": "户外",
               "activity": "表演", "mood": "热闹",
               "tags": ["多人", "舞台", "灯光", "演唱会"],
               "quality": "good", "usable": true}}
  ]
}
```

图片素材：单帧单镜头（`start=0, end=null`）。`summary` 由规则式聚合生成
（确定性、零成本、可测）。

## 六、实测记录（2026-09-24，TMP/_vlm_realtest.py）

**SiliconFlow 模型盘点**（/v1/models）：GLM-4.6V 未上架；可用视觉模型
`zai-org/GLM-4.5V` 与 `Qwen/Qwen3-VL` 系列（8B / 30B-A3B / 32B）。

**A/B 打标**（两段真实素材，抽帧与切分完全一致，仅换模型）：

| 素材 | GLM-4.5V | Qwen3-VL-30B-A3B |
|---|---|---|
| 17.5s 舞台表演 | 5人 · 户外/表演/热闹 · 演唱会 | 6–8人 · 户外草地/表演/热闹 · **夜景、观众** |
| 12.3s 溯溪 | **15人 · 户外溪流/溯溪**（活动识别精准） | 15人 · 户外草地/**攀爬**（场景判为草地，tags 仍含 溪流/岩石） |
| 延迟 | ~15–30s/文件 | ~8–32s/文件（波动大，同量级） |

**定默认 `zai-org/GLM-4.5V`**：场景/活动精度直接决定语义筛选的一次通过率
（「溯溪」vs「草地攀爬」的差距正是典型误选来源）；Qwen3-VL-30B-A3B 作为
快/省备选保留在一个环境变量上。

**e2e 验收**（真实 VLM + 真实渲染）：

- 任务：「帮我剪出和朋友一起的时光：从两个素材里挑多人聚在一起的镜头，拼成
  一段 15 秒左右的视频，素材间用 0.5 秒 fade 转场，输出 OUTPUT/friends.mp4」
- agent 行为：`ls` → `probe_media`×2 → `analyze_media`×2（现场分析）→ 计划
  **3 个 clip**（同源多段：286ed8 的 0–7s 与 8.767–11.267s + sample 的 0–6s），
  `8.767` 正是卡片镜头边界；总时长 14.5s ≈ 要求
- 回验：`{'ok': True, 'duration': 14.5, 'expected': 14.5}`，产物 7.9MB
- 缓存：二次分析 0.001s 命中（`cached=True`）；`/api/inputs?probe=1` 正常带卡片

**离线单测**：`tests/test_content_analysis.py` 19/19（showinfo 解析、长镜头
等分、下采样、缓存命中/失效、坏 JSON 重试、批失败标记、四级降级、图片单帧、
进度事件、`get_vlm_model` 无 key 返回 None 等）。

## 七、已知限制与后续（Phase 4）

- 场景阈值 0.3 / 长镜头粒度 12s / 0.35 分位取帧均为经验值，未调参；真实
  素材漏切或碎切时再动
- VLM 只看画面不听声音——「大家笑得很开心」类音频信号要等 T10 静音/ASR 进卡片
- `auto_select{criteria, budget}` 编译器宏（模型不再手写每个 trim）待卡片质量
  稳定后立项；「上传即索引」后台预分析、原生 video_url 路线（bigmodel GLM-4.6V /
  百炼 qwen3-vl，换 `get_vlm_model` 实现即可）、同伴身份识别（人脸聚类）仍在远期
- 多次分析同一文件且中途换 `VLM_MODEL`：sidecar 不区分模型，需删
  `TMP/probe/<hash>.json` 才会用新模型重打（可接受，日后可在键里加模型名）
