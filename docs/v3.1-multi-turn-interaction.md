# 多轮交互与修订 —— 技术方案（v3.1 · 第三轮修订）

> 目标：把现在「一句话 → 一条成片 → 结束」的一次性流程，改成**可持续交互**的会话：
> 用户看完成片可以继续提修改要求，agent 在上一版基础上增量修改；
> 用户意图不明确、**要求与素材不匹配**时，agent **先反问**而不是硬编计划或默默截断；
> 模型出现**幻觉**时能被发现、被通知、被纠正。
>
> 承接 [v2.0-multi-material-editing.md](./v2.0-multi-material-editing.md) 的
> 「LLM 出计划 JSON → 编译器出命令」架构，**不改变这条分工**。
>
> **修订历史**
> - 第一轮（2026-09-16）：多轮会话载体、ask_user、防静默改动、产物不覆盖。
> - 第二轮（2026-09-17）：① 前端「启动新任务」入口；② 素材不匹配的反问
>   （含 plan_schema 确定性闸门，堵"编造 probe 数据"漏洞）；③ 幻觉通知三层防御
>   （基于 deepagents 0.7.11 源码调研，含 RubricMiddleware 与 HITL 两条原生机制）；
>   ④ ask_user 两种实现方式对比。
> - 第三轮（2026-09-17，本文）：把"素材不匹配"从**时长一个例子**升级为系统性的
>   **Preflight 素材-需求匹配校验**（§5.3c）：语义层（LLM 探测后自检）+ 计划层
>   （确定性 `check_material_fit`）两层，每轮必跑；**关键升级：把"模型修不了的错"
>   （用户可决）从重试闭环里摘出来，直接变成问用户的问题**（§5.3c 末）。
>
> 状态：**P0 已实现并验证**（2026-09-17，离线 31 项 + e2e 4 例全绿）；P1（规则闸门已随 P0 提前落地、diff 卡片、L2 RubricMiddleware）与 P2 待做。

## 1. 需求拆解

| # | 子问题 | 本质 | 主要改动位置 |
|---|---|---|---|
| ① | 会话上下文 | 第二轮要知道"上一版剪成什么样" | 后端（会话存储）+ agent（上下文构造） |
| ② | 意图不明确时反问 | agent 需要一条「不产出计划」的合法出口 | agent（`ask_user` 工具 + 提示词）+ 前端 |
| ③ | 成片可反复调整 | 上一版计划 → 新版计划的**增量修订** | agent + 编译器（diff + 防静默改动） |

## 2. 现状与差距

### 2.1 后端每次运行都是「无状态」的

`web/server.py::_run_pipeline` 每跑一次就 `build_video_agent_v2()` 新建一个 agent，
上下文由 `video_agent.plan_with_retry` 内部写死：

```python
# video_editing/video_agent.py:346
messages: list = [{"role": "user", "content": task}]
```

前端左侧那条"对话"只是**日志展示**，不是会话状态。第二轮说"再改一下"，
对 agent 来说等同于一个全新的、信息缺失的任务。

### 2.2 意图不明确时没有「合法的非计划出口」

`plan_with_retry` 只有两条路径（`video_agent.py:355-368`）：拿到 `submit_plan` → 编译；
拿不到 → 记 `errors`、emit `error`、进入重试。agent 目前**被要求无论输入什么都必须
交出一个计划**——输入"哈哈哈"时只能硬编一个，然后系统报告"成功 + 回验通过"，
这正是项目反复要杜绝的**静默错误执行**。

### 2.3 素材与要求不匹配（④）：当前没有任何系统性校验，且"修不了的错"在错误通道里空转

时长只是用户举的一个例子。把"素材实际能力 × 用户要求"的所有错位方式列出来，
会发现它们**散落在各处、有的查、有的不查、查了的也不告诉用户**：

| 不匹配类别 | 例子 | 现状 |
|---|---|---|
| 裁剪超范围 | 要前 50 秒，素材只有 12.259 秒 | ❌ 不查（§下面的实测） |
| 裁剪空段 | trim_start 已经超出素材时长 | ❌ 不查（`te > ts` 查了，但 `ts` 本身越界没人管） |
| 主轨无声轨 | 要加 BGM / ducking，素材根本没音轨 | ⚠️ ducking 依赖 `has_audio`，但没人拦 |
| BGM 不够长 | `loop=false` 但 BGM 时长 < 成片时长 D | ❌ 不查（音乐中途静默结束） |
| PiP 素材太短 | 视频 PiP 要播 5 秒，素材只有 2 秒 | ❌ 不查 |
| 素材数量不符 | "把那两段拼接"但 INPUT 里只有一段 | ❌ 不查（模型可能硬编一个不存在的 source，被"文件不存在"拦下，但那是另一回事） |
| 引用不存在 / 纯音频当 clip | | ✅ 已查（`_missing_source_msg` 会列出实际可用素材） |
| 叠加/转场超出片段时长 | | ✅ 已查 |

再以"要第一个素材的前 50 秒（实际 12.259 秒）"为例走一遍现在的链路：

1. `plan_schema.validate_plan` 对 video clip 只校验 `trim_end > trim_start`
   和"时长可确定"——**从不把 `trim_end` 和 `probe.duration` 做交叉比对**；
2. 更糟的是 `probe` 字段几乎是**透传袋**（memory 里明确记了"probe 内部不校验"），
   模型如果编造 `probe.duration=60`，"前 50 秒"连编译器的数学都骗过；
3. ffmpeg 按 `-t 50` 跑，实际流只有 12.259 秒 → **输出被静默截断**；
4. 最后 `verify()` 发现成品时长 ≠ 预期 D → 报"回验不一致"。

也就是说：用户要在前 50 秒加的花字/转场全被悄悄扔掉了，最后只得到一句
"回验不一致"，**没有任何环节把这个问题变成"问用户"**。回验失败也不会触发
重出计划（verify 不在重试闭环里）。

**更深一层的结构性问题**：现在所有校验错误都进同一条通道——回传模型、
重出计划、最多重试 2 次。这对"模型写得不对"是对的，但对"素材现实不满足"
是**灾难**："用户要 50 秒、素材只有 12 秒"这种错，**模型重试多少次都修不好**
——不存在能满足要求的计划，只有用户能决定（用全部 / 换素材 / 改范围）。
现状是烧 2 次 LLM 调用、重试 2 次，最后报"计划连续 3 次未通过校验，已放弃"，
用户依然不知道"素材只有 12 秒"这个真正的事实。

**修法 = Preflight 两层 + 错误分流**（§5.3c）：probe 后的语义自检（LLM）、
计划层的确定性匹配校验（程序）；校验错误按**谁能修**分流——模型修得了的
进重试闭环，只有用户能决的直接变成 question 问用户。

### 2.4 幻觉（⑤）：当前只有编译器一层在防，且防不住"口头声称"

已有一层确定性防御：`plan_schema` 的未知字段拒绝 + 素材存在性检查 +
效果白名单。它们能拦住"编造的字段/效果/文件路径"进不了编译器。

但防不住两类：

- **口头声称**：模型在文本里说"已添加背景音乐渐入"，plan 里却没有 `audio` 字段——
  schema 管的是 JSON，管不了散文。用户读文本，以为做了。
- **编造的 probe 数据**：见 §2.3，schema 目前不比对 probe 与 trim 的一致性。

而且即使 schema 报错，"模型出现幻觉"这个事实本身对**用户不可见**——
前端只显示"计划未通过校验：xxx"，用户不知道这是模型在瞎编。

### 2.5 已有的、必须复用的约束

`video_agent._retry_feedback` 注释里的实测结论（多轮设计的硬约束）：

> 刻意**不重放原始消息历史**：① 历史里的 AIMessage/ToolMessage 可能带 provider
> 不接受的内容块，原样回放会 400（SiliconFlow: "Only text and image_url are supported"）；
> ② 把上一版计划原样留在上下文里，模型容易照抄自己的错误答案。

外加 v2.0 的 `plan_schema._unknown_keys`：**计划每一层都拒绝未知字段**，
所有新机制不能成为绕过它的后门。

## 3. deepagents 0.7.11 能力调研（本轮新增）

本项目 agent 基于 `deepagents.create_deep_agent`（0.7.11，安装于 `.venv`）。
对幻觉通知和交互机制，包里**已有现成的轮子**，不用自己造：

### 3.1 自定义 Middleware 通道

`create_deep_agent(..., middleware=[...])` 接受任意
`langchain.agents.middleware.types.AgentMiddleware`，可用钩子：

| 钩子 | 时机 | 能做什么 |
|---|---|---|
| `before_model` / `after_model` | 每次 LLM 调用前后 | 读写 state，检查/改写消息 |
| `wrap_model_call` | 包裹 LLM 调用本身 | 重试、降级、改写请求响应 |
| `wrap_tool_call` | 包裹每个工具执行 | 检查参数、改写结果、记日志 |
| `before_agent` / `after_agent` | 整轮开始/结束 | 汇总级检查 |

**但注意**：本项目 `web/server.py::_stream_agent` 已经用
`agent.stream(..., stream_mode="values")` 拿到了每一步的完整 state——
对 LLM 输出的**可见性 host 侧本来就有**，轻量检查不需要 middleware
（§6 的 L1 就放在 `_stream_agent` 里）。Middleware 的价值在"要在循环内
自动注入修正"的场景（L2）。

### 3.2 RubricMiddleware —— 「幻觉通知到 agent 内部」的原生机制

`deepagents/middleware/rubric.py`：**self-evaluated agent iteration**。

- 调用时在 state 里传 `rubric`（一段"什么叫完成/合格"的自然语言标准）：
  `agent.stream({"messages": [...], "rubric": "..."})`；
- agent 每次"以为自己做完了"（返回无工具调用的响应）时，middleware 自动召一个
  **grader 子 agent** 拿 transcript 对照 rubric 打分；
- grader 判 `needs_revision` → 把评语作为 `HumanMessage` **注入 agent 循环，
  agent 自动重出计划**——这就是"通知到 agent 内部"的字面实现，不需要人工介入；
- 判 `satisfied` → 放行；判 `failed` / `max_iterations_reached` / `grader_error`
  → 不改写模型响应，但状态里留 `_rubric_status`，并有 `rubric_evaluation_end`
  流事件——host 读出来 emit 给前端，告知"自动纠偏失败，请人工确认"。
- 构造参数含 `model`（grader 用哪个模型）、`max_iterations`（默认有上限）、
  `on_evaluation` 回调（可拿到每次评分明细 → 正好用来 emit 幻觉事件）。

**对本项目的映射**：rubric 写成三条——
① 计划 JSON 里声称的每个效果/叠加/音频都必须真实存在于计划对应字段；
② 引用的每个 INPUT/ 文件必须真实存在；
③ clip 的 probe 数据必须与 transcript 中 probe_media 的返回一致。

### 3.3 HumanInTheLoopMiddleware / interrupt_on —— 另一条交互路线

`create_deep_agent(..., interrupt_on={...})`（deepagents 自己也在用它实现
filesystem 权限确认）：图执行到指定工具调用前**中断挂起**，人工批复后从
checkpoint 恢复继续。

用于 `ask_user` 就是"方案 B"（§7）：agent 原地等用户回答，一轮内完成问答。
代价：需要 checkpointer + resume 端点 + 前端状态机，`_stream_agent` 的单次
流式模型要改成"可中断-可恢复"。

### 3.4 调研结论

| 需求 | 原生机制 | 采用 |
|---|---|---|
| 幻觉自动纠偏（深度） | `RubricMiddleware` | ✅ L2（§6） |
| 幻觉轻量标记（便宜） | host 侧扫描（不需要 middleware） | ✅ L1（§6） |
| 确定性拦截 | `plan_schema`（已有 + 本轮增强） | ✅ L0 |
| 原地等人回答 | `interrupt_on` + checkpointer | ⏸ 方案 B，P2 可选 |
| 下一轮消息回答 | `ask_user` 工具直接返回 | ✅ 方案 A，P0 采用 |

## 4. 核心设计决策

### D1. 多轮的载体是「上一版计划 JSON」，不是「消息历史」

会话状态里存结构化事实（`task / last_plan / last_output / last_verify / turn`），
理由同第一轮：规避 provider 400（只回传纯文本）、计划是唯一可信中间态、
指代消解天然成立（"那个转场" = `last_plan.timeline[i].transition`）。

### D2. 修订 = 带上一版计划重出**完整**计划 + 防静默改动闸门

不引入补丁格式（`plan_schema` 会拒未知字段）。配套：编译器 `diff_plans()`
展示变更项；后端强制产物换名（D4）。

### D3. `ask_user` 作为「不产出计划」的合法出口

与 `submit_plan` **互斥**，同一轮只能用一个。四种触发条件（本轮加第 4 条）：

| 触发条件 | 例子 | 期望反问 |
|---|---|---|
| 无剪辑动作 | "哈哈哈" | 给能力菜单让用户选 |
| 素材指代不明 | "给那个视频加转场"（INPUT 有 3 个） | 列出真实候选 |
| 超出能力 | "做个动态贴纸" | 如实说做不到 + 给替代 |
| **要求超出素材实际** ⭐新 | "第一个素材的前 50 秒"（实际 12.259s） | 报真实时长，给选项：用全部 / 换素材 / 改范围 |

拿到 `ask_user` 时 emit `question` 事件**直接返回，不重试、不算失败**。

### D4. 修订时产物不覆盖（后端强制）

新计划 `output.filename` 与 `last_output` 相同时自动加 `-r2` 后缀，
不靠模型自觉（否则没法对比修改前后）。纯字符串处理，模型绕不过。

### D5. 规则闸门只做「高置信度负例」

纯规则拦"一眼没意图"的输入（"哈哈哈"），其余进 agent 由 `ask_user` 兜底。
规则错了最多是"少问一次"，不会拦死正常需求。

### D6. 会话存进程内，前端持有 id；「启动新任务」= 换 id + 清上一任务的素材

单用户本地工具，`SESSIONS: dict` 足够。前端持 `crypto.randomUUID()` 存
localStorage。「启动新任务」先调 `POST /api/session/reset` 把上一任务上传的
素材清除，再换新 id 开始新一轮循环；未知 id 无状态兜底（当第一轮）。

**素材归属不按会话记在内存里**——`SESSIONS` 一重启就丢，旧任务的素材会
永远清不掉（INPUT/ 对 agent 又是全局可见的）。归属以落盘的
`TMP/uploads.json` 白名单为准：上传即进白名单，reset 一次清空白名单里全部
文件（单个失败不拖垮整组），重启也不受影响；手动放进 `INPUT/` 的文件与
示例素材不在白名单内，不会被 reset 清除。任务运行中（`RUN_LOCK` 占用）
reset 直接拒绝，防止删掉正在渲染的源文件。会话本身仍只在内存
（`--force` 重启丢对话上下文可接受，素材清理不受影响）。

### D7. 幻觉防御按「成本递增」分三层，每层职责单一

L0 拦截（确定性，已有+增强）、L1 标记（毫秒级规则，只通知不拦截）、
L2 纠偏（LLM grader，自动注入修正）。详见 §6。**绝不把三层揉成一层**——
成本和误伤率差着数量级。

### D8. 素材-需求匹配 = 每轮必过的 Preflight，但校验点不在"对话开始前"，而在两个能落地的地方

用户提的方向完全正确：**每轮都要校验"素材 × 要求"是否匹配，不匹配就不向下走**。
但"每次对话开始之前"这个时点落不了地——那时手里只有一句自然语言，
"剪得更有电影感"没法被确定性程序校验。必须等两样东西之一出现：

1. **LLM 已探测素材** → 语义判断"要求能否被这些素材满足"（Tier 1）；
2. **计划 JSON 已生成**（要求已被结构化为 plan）→ 确定性交叉比对（Tier 2）。

所以 Preflight 分两层，每轮（含修订轮）必跑：

- **Tier 1 语义层**（在 agent 内，probe 之后、submit_plan 之前）：
  探测完先自检"要求的每一项是否都能被探测事实满足"，不满足 → `ask_user`。
- **Tier 2 计划层**（在 host，submit_plan 之后、compile 之前）：
  `check_material_fit(plan)` 确定性比对，**以服务端缓存的真实 probe 为准**
  （不是 plan 里模型自报的 probe——那正是编造数据的藏身之处）。

配合一条**错误分流**原则（本方案最重要的结构性升级）：

> **模型修得了的错 → 重试闭环；只有用户能决的错 → 直接问用户。**

"素材只有 12 秒"属于后者——不存在能满足要求的计划，问模型多少次都白搭。
Tier 2 输出的每个 mismatch 都带 `user_decidable` 标记，false 进重试、
true 直接 emit `question`（带真实数据 + 选项），**零重试**。

## 5. 具体改动

### 5.0 agent 内部是怎么跑的（控制流说明，回答"是不是多子任务/钩子"）

**不是多子任务，也不是钩子函数驱动**——agent 内部是**单个 ReAct 循环**
（`create_deep_agent` 的本质）：模型读上下文 → 决定调工具 → 看结果 →
再决策，直到自己决定交 `submit_plan` 或 `ask_user`。循环里**没有 phase 划分**，
"ls → probe → 自检 → 产出"是同一个循环中的步骤，节奏由模型自定
（probe 几次它说了算）。

| 机制 | 在哪 | 性质 |
|---|---|---|
| 可行性自检（Tier 1） | agent **内部**，循环里 | **提示词协议（软约束）**：Workflow 第 2.5 步把顺序写给模型看，模型大概率照做，但不保证 100% |
| 素材匹配校验（Tier 2） | **循环外**，host | **确定性硬闸门**：`submit_plan` 是循环内的普通工具调用，没有"计划已完成"这个可由程序拦截的时点；可靠的拦截点只在 host 收到计划之后 |
| 幻觉 grader（L2） | agent 内部，但用现成钩子 | `RubricMiddleware` 挂在"agent 以为做完了"这个确定时点上——**这是钩子的正确用途** |

两个"多轮"不要混淆：**用户驱动的多轮** = 多次 HTTP 请求，每次重建 agent、
纯文本重建上下文（D1）；**agent 内部的"轮"** = ReAct 循环自身的迭代。
前者是本方案加的，后者是 deepagents 本来就有、且保持不动的。

### 5.1 前端：「启动新任务」入口（本轮新增）

- 输入区工具栏有 `[启动新任务]` 扁平按钮（`.btn-flat`）。
- 点击行为：
  1. 先 `POST /api/session/reset`（带旧 session_id）——**把上一任务上传的
     素材全部清除**（后端以 `TMP/uploads.json` 白名单为准整组清空，单删失败
     不拖垮整组；任务运行中后端拒绝，前端报错并**保持当前会话不变**）；
  2. `session_id = crypto.randomUUID()`（存回 localStorage）——对应 agent 侧
     "开启新一轮循环"（turn 归零、无 base_plan）；
  3. 清空左侧对话（`#msgs` 重置 + 欢迎语）；
  4. `resetPanels()` 清空右栏流水线卡片（**保留素材卡片**）；
  5. `loadInputs()` 重新拉取 `/api/inputs`——此时列表就是清空后的新素材组，
     手动丢进 `INPUT/` 的文件也会在此刻出现；
  6. 输入框 placeholder 回到第一轮的"描述要剪成什么样"。
- **素材归属**：上传即记入落盘白名单 `TMP/uploads.json`（不按会话记内存，
  服务重启不丢）；单个删除（`/api/delete`）同步从白名单移除。
  手动放进 `INPUT/` 的文件和示例素材**不在白名单内，不会被 reset 清除**。
- **会话生命周期**：一个 `session_id` 从首轮一直持续到用户点「启动新任务」为止；
  期间的每条用户消息都按"修订轮"处理（有 `pending_question` 按问答接续、
  有 `last_plan` 按修订 brief，见 §5.4）。中途上传/删除素材**不重置会话**——
  修订 brief 每轮都带当前 INPUT/ 实际素材列表，素材变更自然生效。
- 正在运行（`busy`）时禁用该按钮，避免一局跑到一半开新局把右栏冲掉。

### 5.2 agent 侧（`video_editing/video_agent.py`）

**(a) `ask_user` 工具**（同第一轮）：
```python
@tool
def ask_user(question: str, options: list[str] | None = None) -> str:
    """Ask the user to clarify an ambiguous, unsupported, or infeasible request.
    Use INSTEAD of submit_plan. Args: question; options (optional candidates)."""
    return "问题已提交给用户，等待答复。"
```
注册进 `build_video_agent_v2` 的 tools。

**(b) 提示词新增三段**（插在 `V2_SYSTEM_PROMPT_TEMPLATE` 的 Workflow 后）：

- **「可行性自检」（Workflow 第 2.5 步）**：把 Workflow 改成
  `ls → probe_media → 可行性自检 → submit_plan / ask_user`。自检要求：
  > 对照 probe_media 返回的真实数据，逐项检查用户要求是否能被满足
  > （裁剪范围是否在时长内、音轨是否存在、素材数量对不对、分辨率/画面
  > 内容是否符合要求描述的素材）。**任何一项不满足，不要硬凑计划**——
  > 调用 ask_user，如实报告探测到的事实，并给出可行的选项。
- **「何时先反问」**：同第一轮三种条件，加第 4 条（即自检失败的出口）：
  > 当你通过 probe_media 发现用户要求的范围超出素材实际能力时（例如要前 50 秒
  > 但素材只有 12.259 秒），**不要硬截断、也不要编造 probe 数据凑数**——
  > 调用 ask_user，如实报告真实时长，并给出选项（用全部 / 换素材 / 改范围）。
- **「probe 数据的真实性」**：明确告知模型 plan 里的 `probe` 字段必须与
  probe_media 的实际返回一致，编译器会以**服务端重新探测的结果**为准做
  交叉校验，编造会被打回。

**(c) `extract_ask(result)`** 与 `extract_plan` 同构。

**(d) `_revision_brief(task, base_plan, base_output, materials)`**（同第一轮，
纯文本重建，含当前 INPUT/ 实际素材列表）。

**(e) `plan_with_retry` 增加参数** `base_plan / base_output / materials`；
拿到 `ask_user` → emit `question` → 立即 return；编译失败重试仍走
`_retry_feedback` 且保留"这是修订"语义。

**(f) L2 挂 RubricMiddleware**：`build_video_agent_v2` 增加可选参数
`rubric: str | None`，非空时：
```python
from deepagents.middleware.rubric import RubricMiddleware
create_deep_agent(..., middleware=[
    RubricMiddleware(model=get_model(), max_iterations=2, on_evaluation=on_eval)
])
```
`on_evaluation` 回调里把每次评分 emit 成 `hallucination` 事件（level=info/warn）。
rubric 文本见 §3.2 末。用环境变量 `V2_RUBRIC=1` 控制开关，默认关（P1 再开）。

### 5.3 schema / 编译器侧

**(a) 新增 `plan_schema.check_material_fit(plan, project_root) -> list[Mismatch]`**
（Preflight Tier 2，**每轮必跑**，submit_plan 之后、compile 之前）

返回**结构化** mismatch（不是纯错误字符串）：

```python
@dataclass
class Mismatch:
    type: str          # 见下表
    tag: str           # 出问题的位置，如 "clips[0].trim_end"
    requested: object  # 用户/计划想要的
    actual: object     # 素材实际有的
    user_decidable: bool
    message: str       # 可直接展示给用户的中文事实陈述
```

三条铁律：

1. **一律以服务端缓存的真实 probe 为准**（`server._probe_file`，带 mtime 缓存，
   成本毫秒级）——不信任 plan 里模型自报的 `probe` 字段；
2. **顺带比对 plan.probe 与真实 probe**（时长/分辨率/音轨不一致即记
   `probe_mismatch`，这本身就是 L1 的幻觉信号）；
3. 与 `validate_plan` **分工**：后者管"计划合不合法"（结构/白名单/引用），
   前者管"计划与素材现实合不合"——两个函数，`compile_plan` 里依次调用。

不匹配分类（覆盖时长之外的全部类别，即 §2.3 表）：

| type | 判定 | user_decidable |
|---|---|---|
| `over_range` | `trim_end` > 真实时长 | ✅ |
| `empty_range` | `trim_start` ≥ 真实时长 | ✅ |
| `no_audio_track` | 计划要 ducking/混音但主轨 `has_audio=false` | ✅ |
| `bgm_too_short` | `audio.loop=false` 且 BGM 真实时长 < D | ✅ |
| `pip_too_short` | 视频 PiP 的 `duration` > 源素材真实时长 | ✅ |
| `source_missing` / `no_video_track` | 引用不存在 / 纯音频当 clip | ✅ |
| `probe_mismatch` | plan.probe 与真实 probe 不符 | ❌（回传模型纠正） |
| `bad_reference` / `unknown_key` / 数学错 | schema 违规 | ❌ |
| `upscale` / `fps_up` | 输出分辨率 > 源 2× / 帧率上调 | ⚠️ warn 级，**不阻断**，emit 提示 |

**(b) 错误分流：`plan_with_retry` 升级成三分支**（本方案最重要的结构性改动）

```python
result = invoke(messages)
ask = extract_ask(result)
if ask:                        # 分支 ① agent 自己反问（Tier 1 出口）
    emit(question); return

plan = extract_plan(result)
mismatches = check_material_fit(plan, project_root)
decidable = [m for m in mismatches if m.user_decidable]
if decidable:                  # 分支 ② 素材现实不满足 → 问用户，零重试
    emit(question, options=由 mismatch 生成)
    return                     # last_plan 不变，等用户下一条消息
errors = validate_plan(plan, project_root)
if errors:                     # 分支 ③ 模型修得了的 → 现有重试闭环
    ...（原逻辑，反馈里保留"这是修订"语义）
```

分支 ② 的 question 由 mismatch 直接生成，例如 `over_range` →
"素材 a.mp4 实际时长 12.259 秒，你要：1) 用全部 12.259 秒 2) 换别的素材
3) 改范围（如前 10 秒）"。**不再出现"烧 3 次 LLM 后报放弃、用户依然不知情"**。

**(c) `diff_plans(old, new)`**（第一轮已定）：flatten 成 `path→value` 再比对。

### 5.4 后端（`web/server.py`）

- `SESSIONS: dict[str, dict]` + `SESSION_MAX_TURNS = 5`（同第一轮）。
  会话字段：`task / last_plan / last_output / last_verify / turn /
  pending_question`——`pending_question` 记录最近一次 question 事件
  （问题文本、选项、类型），是"提问 → 回答"接续的桥梁。
- **每轮消息构造按优先级三选一**：
  1. **有待答问题**（`pending_question` 非空）→ 构造"问答接续"上下文：
     "你刚才问用户：…。用户回答：…。请据此继续（若是素材不匹配，
     按用户的选择修正计划并重新 submit_plan；若回答与问题无关，
     就当作新的要求处理）"。
  2. **有上一版计划**（`last_plan` 非空）→ `_revision_brief`（修订）。
  3. **都不是** → 首轮单条消息。
  
  一轮成功提交新计划后清除 `pending_question`；该轮再次 question 则更新它。
  三种构造**都只用纯文本**，遵守 D1 的 provider 兼容约束。
- `_run_pipeline(task, emit, session_id)`：
  - 取/建会话 → `_intent_gate(task)`（D5，纯函数）→ 命中 emit `question`、
    写入 `pending_question` 后返回；
  - 编译前比对 filename 与 `last_output`，同名自动加 `-r{n}`（D4）；
  - `plan_with_retry(..., base_plan=..., base_output=..., materials=...)`，
    **并把服务端的 `_probe_file` 缓存探针以 `probe_fn` 回调传进去**
    （`plan_schema` 不能 import `server`，反向注入，Tier 2 才能拿到真实 probe）；
  - L1 幻觉扫描挂在 `_stream_agent` 的消息循环里（§6）；
  - 拿到 `question` 更新会话（记问题、**不写 last_plan**）；
  - 成功 → 更新 `last_plan / last_output / last_verify`，emit `plan` 附 `diff`。
- `/api/run` 请求体加 `session_id`（缺省兼容，当第一轮）。

## 6. 幻觉三层防御（本轮重点）

```
LLM 输出（计划 JSON + 文本声明）
        │
  L0  plan_schema 确定性校验        ← 已有 + 本轮交叉校验增强
        │ 拦截：未知字段/效果/文件不存在/超时长 → 错误回传重出（现有闭环）
        ▼
  L1  host 侧启发式扫描              ← 新增，毫秒级，只标记不拦截
        │ 命中：emit hallucination(warn)，前端在消息旁显示"此处疑似与实际不符"
        ▼
  L2  RubricMiddleware grader       ← 新增，LLM 评审，needs_revision 自动注入修正
        │ failed / max_iterations：emit hallucination(error)，告知用户人工确认
        ▼
  交付（成片 + 可能的幻觉标记）
```

### L0 —— 编译器/schema（拦截层）

已有：未知字段拒绝、效果白名单、素材存在性。
本轮增强：`check_material_fit`（§5.3a）——以服务端真实 probe 为准的
素材-需求匹配校验族（超范围 / 空段 / 无声轨 / BGM 太短 / PiP 太短……），堵住
"编造 probe 数据让超范围需求过检"的漏洞（§2.3 的实测路径）。

职责：**让幻觉进不了编译器**。误伤率 ≈ 0，成本 ≈ 0。

### L1 —— host 侧扫描（标记层，纯规则）

在 `_stream_agent` 的既有消息循环里，对每条新 `AIMessage` 跑
`_hallucination_scan(msg, inputs, probe_results)`：

| 信号 | 判定 |
|---|---|
| 文本声称的效果名不在 `skills.SKILLS` 注册表 | "声称做了不存在的能力" |
| 文本/工具参数里出现的 `INPUT/xxx` 不在实际目录 | "引用了不存在的素材" |
| `probe_media` 返回错误，模型仍按成功结果引用其数据 | "用了失败的探测结果" |
| 文本声称的叠加/音频，plan 里无对应字段 | "声称与计划不符" |

命中 → emit `{"type":"hallucination", "level":"warn", "signal":..., "evidence":...}`。
**只通知、不拦截**：启发式有误报，打断正常流程的代价大于收益。

前端展示约定：`warn` 在该条消息右上角加琥珀色「疑似幻觉」徽标，
hover 显示 evidence；`error`（来自 L2 失败）用红色。

职责：**让用户看见"模型这话靠不住"**。成本毫秒级，可常开。

### L2 —— RubricMiddleware 自动纠偏（深度层）

见 §3.2。agent 每次"以为做完了"时 grader 子 agent 对照 rubric 审 transcript：
`needs_revision` → 评语注入循环、自动重出计划；
`satisfied` → 放行；`failed/max_iterations_reached` → host 读出 `_rubric_status`
emit `hallucination(error)` 告知用户。

职责：**在不惊动用户的前提下自动纠偏**。成本 = 每轮 1~N 次 grader LLM 调用，
用 `V2_RUBRIC=1` 开关控制，P1 阶段默认开（多轮修订时尤其值得：
修订请求往往只点一处，grader 能抓"顺手乱改"）。

### 为什么必须三层

- 只有 L0：口头声称无人管（§2.4），且"回验失败"这种后置信号太迟；
- 加 L1：用户能看见了，但模型不知道自己错了，不会改；
- 加 L2：模型被自动纠正了，但 grader 又贵又慢，不能什么事都惊动它。
  所以 L1 常开（便宜）、L2 开关控制（贵）、L0 永远在（免费）。

## 7. ask_user 实现方式对比（A/B）

| | 方案 A：工具直返（第一轮方案） | 方案 B：deepagents 原生 HITL |
|---|---|---|
| 机制 | `ask_user` 立即返回；问题推给前端；用户**下一轮消息**作答 | `interrupt_on={"ask_user": ...}` + checkpointer；图在工具前中断，**原地等**用户答案 POST 回来后恢复 |
| 架构改动 | 无（与现有单次请求-响应流兼容） | 大：checkpointer、resume 端点、前端状态机、`_stream_agent` 改可中断-恢复 |
| 用户体验 | 问答隔一轮，自然符合"对话"心智 | 一轮内完成，更像表单 |
| 会话关系 | 答案天然成为下一轮输入，与 D1 会话机制**同构** | 答案注入当前线程，需与会话存储额外打通 |
| 风险 | 模型可能在拿到答案前继续乱跑（靠"ask_user 后停止"提示词约束） | 中断/恢复的边界情况多（超时、并发、刷新） |

**推荐：P0 用 A**（改动小、与 v3.1 其余机制自洽），**B 作为 P2 可选项**——
如果实际使用中"问答隔一轮"被用户明确诟病，再切换到 B，届时 D1 的会话机制
依然复用（B 只是把"下一轮消息"换成"同轮 resume"）。

## 8. 交互时序（更新版）

```
【第 1 局 · 第 1 轮】用户："把 INPUT/a.mp4 和 b.mp4 拼起来，中间加 0.5 秒 fade"

   双重打回——编造数据骗不过 Tier 2）

【第 2.5 轮】用户回答："那就用全部时长"

  "按选择修正计划重新提交"的指令）→ agent 产出 trim_end=12.259 的计划
  → 正常编译执行；pending_question 清除

【第 3 轮】用户："输出换成 1080p"
  后端自动改名 final-r2.mp4（D4）→ 修订 brief 带 P1
  → agent 只改 output.resolution → diff 卡片只显示这一条
  → L2 grader 复核："除分辨率外与上一版一致" → satisfied

【用户点「启动新任务」】session_id 换新 → 对话清空 → 素材列表刷新
  → 后端见新 id 建空会话 —— 新一轮循环开始
```

## 9. 风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| provider 400 | 回放带内容块的历史 | D1：只回传纯文本 plan（沿用既有约束） |
| 静默改动 | 模型顺手改用户没提的字段 | 产物改名强制 + diff 展示 + L2 grader |
| 编造 probe 数据 | "前 50 秒"配 `probe.duration=60` | L0 交叉校验（§5.3a）+ prompt 明示 |
| 规则闸门误伤 | "剪掉前5秒"被当闲聊 | 只做负例 + 关键词表覆盖剪辑动词 |
| 反问过于敏感 | 频繁反问惹人烦 | 限定四种触发条件 + 正反例提示词 |
| L1 误报 | 正常消息被打"疑似幻觉" | 只标记不拦截；L2 用 LLM 复核兜底 |
| L2 成本 | 每轮多烧 grader 调用 | `V2_RUBRIC` 开关 + `max_iterations=2` 封顶 |
| 会话丢失 | `--force` 重启 | 无状态兜底（未知 id 当第一轮），产物在 OUTPUT/ 可查 |
| 重试语义混淆 | 用户修订失败被自动重试烧算力 | 重试反馈保留"这是修订"；连续同错提前收手（现有逻辑） |

## 12. 与现有设计原则的一致性

1. **不靠模型自觉，靠结构性约束**（v2.0 方法论）
   → 产物改名后端强制；交叉校验确定性；L0 永远在；幻觉通知有专门事件通道。
2. **失败要显性，不能静默**（`plan_schema` 注释原话）
   → `ask_user` 让"做不到/说不清/素材不够"变成正常可见事件；
   `hallucination` 事件让"模型在瞎编"从"回验不一致"这种模糊信号
   变成**具体、可定位、分级**的显性通知。
3. **LLM 出意图、编译器出工程**
   → 本轮所有新增（交叉校验、L1 扫描、diff）都是确定性程序，没有一个滤镜/命令是 LLM 写的；
   RubricMiddleware 的 grader 只负责"判断对错"，改计划的仍然是主 agent。
4. **优先用平台原生机制**（本轮新增）
   → RubricMiddleware / interrupt_on 是 deepagents 0.7.11 自带的能力，
   方案优先复用而不是自造轮子；自造的部分（L1、交叉校验）都是
   `agent.stream` 可见性够得着的轻量逻辑。
