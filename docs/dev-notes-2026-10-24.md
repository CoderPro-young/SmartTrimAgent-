## 一、修复（按发现顺序）

### R4 · V8.2 节拍卡点污染 last_plan（修订轮熔断的根因）

- **事故链**（场景 A 轮 5）：`_snap_to_beats` 编译期直接改写 clip 的
  `trim_end` 但不同步收缩挂在该片段的 overlay → 校验时 overlay 按旧 trim
  对齐合法、snap 后 last_plan 自相矛盾 → 下一轮修订以它为 base 重新校验
  报 4 处越界 → 叠加 R5 的指令冲突 → 重试耗尽熔断（用户任务失败）。
- **修复**（plan_compiler.py）：`_shrink_overlays_after_snap`——snap 缩短
  clip 时同步收缩尾部超界 overlay、移除整条落在片段外的 overlay
  （duration 必须为正，压 0 不合法）；snap 后计划必须仍通过 validate_plan。
- **测试**：test_v81_features t09b（含浮点边界教训：Δ 恰等 BEAT_SNAP_MAX
  时浮点误差会落在跳过侧，测试用 Δ=0.3）。

### R5 · 修订轮回传的指令冲突 + 例外出口无底稿（熔断的放大器）

- **事故形态一**（校验失败路径）：`_retry_feedback` 的 ops_mode 处理只在
  plan=None 分支实现；plan 非 None 的校验失败回传机械要求 submit_plan，
  与修订 brief 的「只允许 edit_plan」同上下文矛盾 → 模型摆烂纯文本 →
  提取失败 ×2 → 短路。
- **事故形态二**（例外出口无底稿）：给了「ops 覆盖不到允许 submit_plan」
  的例外出口后，模型仍两轮纯文本——修订 brief 刻意只给片段表不给完整
  JSON，模型没有底稿不敢凭空重写。
- **修复**（video_agent.py）：① 校验失败/提取失败两条路径统一给出岔路
  指引（ops 能修的修 ops；ops 覆盖不到的字段本轮例外允许 submit_plan；
  plan=None 时给 edit_plan/submit_plan/ask_user 三出口）；② ops_mode 的
  回传附上一版完整计划 JSON 作底稿（低频例外路径，正确性优先）。
  期间还修掉自己引入的 UnboundLocalError（instruction 挪进 else 分支后
  plan=None 路径引用未定义变量——测试盲区，t16 补齐）。
- **测试**：test_v9_understanding t16。

### R6 · 修订轮防覆盖失效（自己上午引入的回归）

- last_output 改存实际产物名（带 _preview）后，防覆盖比较
  `fn == base_output` 两侧口径不一致永远不相等 → 修订轮悄悄覆盖上一版
  成片（场景 B 轮 2 实测：slideshow_preview.mp4 被同名覆盖）。
- **修复**（video_agent.py）：判定抽成 `_guard_overwrite`，按本档实际
  产物名（`output_filename(plan, {"preview": ...})`）比较。
- **测试**：test_v9_understanding t17（防覆盖此前无任何用例，故回归拦不住）。

### R7 · 渲染失败照发 done 且污染会话「上一版」位

- **事故链**（场景 C 轮 1）：归一化失败后仍走到 verify→done(ok=false)，
  无 error 事件（run_errors.log 不落）；且 `_commit_compiled` 在执行前已
  把失败计划写进 last_plan/last_output → 下一轮修订 brief 引用一个不
  存在的成片，agent 拿错误事实判断（问用户「重复提交？」）。
- **修复**（server.py）：① 命令级失败发 error 事件（含失败命令与 stderr
  尾巴，顺带触发 run_errors.log 落盘）；② `_execute_compiled` 返回成功
  与否，三个调用点改为**先执行后提交**——渲染失败的计划不占「上一版」位。

### R8 · detect/normalize 同池并行（V7 埋的雷，prepass 任务必炸）

- **事故链**（场景 C 轮 1 的归一化 rc=-2）：`execute` 把 detect 与
  normalize 放同一 ThreadPoolExecutor——但 normalize 的输入恰恰是
  detect（face_mosaic prepass，渲染 87s 素材数分钟）的产物！归一化启动
  即读半成品 rc=4294967294；exec 事件按完成顺序发还掩盖了真实时序
  （手动重跑同命令成功是定位的分叉点）。V7 并行化假设「detect/normalize
  相互独立」在 prepass 场景不成立，V7 之后首个真实 prepass 任务踩中。
- **修复**（plan_compiler.py）：分两批——detect 批（批内并行）完成后再
  并行 normalize；render 保持串行。
- **测试**：test_v7_workflow t15（mock 计时断言 normalize 启动晚于全部
  detect 完成，且 normalize 批内并行保留）。
- **真实验证**：simtest6 干净跑通（20.0s 打码成片）；同参数重跑时
  prepass 产物「存在即跳过」复用（09:17 产物直接命中，免数分钟重渲染）。

### R1 真实闭环（10-23 修复的渲染级验证）

改打码参数（blur/块10）→ 新指纹产物 `c1_face_mosaic_cafc0129.mp4`
（与旧参数产物 f3a81902/b45ae70a 并存，字节数不同）→ 归一化缓存自动
失效。旧固定名时代这里会命中旧缓存出旧效果。三个指纹产物同时在盘即证。

## 二、观察项（不修，记录）

1. **ops 词汇表两处能力缺口**（两次不同场景撞上）：改既有效果参数
   （face_mosaic 的 mode/block_size）与 overlay 操作（加标题）都不在
   ops 词汇表，agent 只能走 ask_user 或例外 submit_plan 重写。高频用户
   动词，建议下轮扩 ops：`set_effect_args`（改效果参数）+
   `add_overlay/remove_overlay`。扩了之后 R5 的例外出口使用率应大幅下降。
2. **ask_user 接续路径的约束力弱**：场景 C 轮 2 用户答「重写整份计划用
   blur 块10」，agent 重写成 9 片段 78.8s 大合集（用户意图只是改 20s
   视频的打码参数）。校验失败路径有底稿+「只改问题处」约束，ask_user
   接续（build_answer_brief）没有等价约束。扩 ops 词表可部分缓解。
3. **首次提交失误率**（Flash）：overlay 越界（场景 A 轮 2/3 各一轮）、
   narration 臆造字段（10-23）——全部一轮重试内自愈，T6 的实测证据继续
   攒着。
4. agent 探测阶段会 probe 全部素材（含任务未提及的）——少量冗余，无害。
