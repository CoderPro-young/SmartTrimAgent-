# SmartTrimAgent 后续改进方向 —— 脏活自动化 × 小白快速出片

> 2026-09-13 ｜ 基于《案例对比报告》《时刻Pro/剪映补充深挖》与定位讨论收敛而成。
> 定位一句话：**不帮用户生成高创意内容；帮新手小白和刚接触剪辑的人快速出"能用"的片，
> 把去水印、加字幕、配 BGM、转场、打码这类脏活粗活累活全部自动化。**

---

## 一、为什么这个定位成立（两个 case 的交叉论证）

**剪映的 68 分实测恰好是定位合理性的证明。**
36氪测评的结论是"效率拉高几倍，但只能从 0 做到 60 分，不懂情绪递进、模板感重"。
注意：**这个批评对专业创作者是缺点，对小白恰恰是够用的**——小白要的就是
"快速得到一个结构完整、节奏规整、挑不出毛病的及格片"。剪映 10 亿用户盘子里，
最大的群体本来就是这个需求。我们不碰它"高光 60 分以上"的地带，只做 0→60 这一段。

**Avid 的行业调研给这个定位背书。**
79% 职业剪辑师已在用 AI，最高频用途是语音转文字（60%），87% 认为 AI 的价值在于
"更高效地实现自己的意图"——**连专业用户都优先把 AI 用在脏活上**，小白更是如此。

**时刻Pro证明"快速出片"本身就是一个完整产品。**
87% 自然语言成功率、2025 年 1.2 亿条、83% 导出后直接分享——用户付费的就是
"拿到能直接发的东西"。它没有试图做创意表达（那是 PanoMind 端侧高光精选的事），
云端时刻Pro 的卖点就是"一分钟出能用的片"。

**我们的差异化：剪映的两个实测坑，恰好是我们架构的原生强项。**

| 剪映实测问题 | 根因 | 我们的对应机制 |
|---|---|---|
| 组合指令常漏执行一两项 | 命令式架构：子 Agent 各干各的，无全局合成层 | 声明式计划 JSON：编译器统一校验，漏项/越界**显式报错** |
| "生成快、审核慢"，配错画面不提示 | 无程序化质量门禁，审核转嫁给用户 | ffprobe 回验 + 程序化审阅报告（见 R3），**审核也快** |

## 二、能力矩阵：脏活清单盘点

| 脏活 | 现状 | 技术路径 | 诚实边界 |
|---|---|---|---|
| 拼接/裁剪/画幅/转场 | ✅ 已有 | — | — |
| 人脸打码 | ✅ 已有（YuNet） | — | — |
| 花字/水印文字 | ✅ 已有（drawtext） | — | — |
| **去水印** | ❌ | `delogo` 滤镜（指定区域遮盖） | 是"糊掉"不是 AI 消除（inpainting），效果档次低于剪映，但对固定位置 logo 够用；需诚实告知用户 |
| **加字幕** | ❌ | faster-whisper ASR → SRT/ASS → subtitles 滤镜烧录 | 本地小模型，免费；口播类素材效果好，嘈杂环境需人工抽查 |
| **配 BGM** | ❌ | 音频轨：`amix` + 转场 `acrossfade` + ducking | 用户指定音频文件；自动选曲不做（那是音乐推荐，不是剪辑） |
| **自动转场** | ⚠️ 半成品 | 场景切分（`select='gt(scene,0.3)'`）+ 在切点自动插 xfade | 需先有场景切分信号（恰好是脏活版内容理解的第一项） |
| **剪静音/剪口播** | ❌ | `silencedetect` → 静音区间列表 → 编译器展开成 trim 序列 | "剪掉所有静音"= 编译器一次循环；口播去"嗯啊"需 ASR 配合（二期） |
| **多规格一键输出** | ❌ | plan schema 的 output 改 variants 数组，编译器循环实例化 | 9:16/16:9/1:1；智能裁剪跟主体可后置，第一版居中裁 |

**注意**：这张表里唯一需要"模型"的只有 ASR（L2 专用小模型）。
去水印/字幕烧录/BGM/转场/剪静音全部是 ffmpeg 确定性能力——
**脏活定位的最大红利：几乎不引入 LLM 不确定性，天然落在"工程正确性归程序"的既有路线上。**

## 三、路线：三个阶段

### R1 · 能力面：Skill 注册表 + 补齐五个脏活（最优先）

**先修地基——Skill 注册表（原 P1-1 提级为 R1 首项）：**

```python
SKILLS = {
  "delogo":       Skill(args_schema={...}, to_vf=..., prompt_doc=...),
  "subtitles":    Skill(args_schema={...}, to_vf=..., prompt_doc=...),
  "bgm":          Skill(args_schema={...}, to_af=..., prompt_doc=...),
  "auto_xfade":   Skill(args_schema={...}, needs=["scene_cuts"], to_filter=..., ...),
  "trim_silence": Skill(args_schema={...}, needs=["silence_ranges"], ...),
  "face_mosaic":  Skill(...),  # 现有能力迁入
}
```

schema 校验、命令生成、提示词文档全部从注册表派生——
**一处定义同时消灭"新增 effect 同步三处"的坑和"模型猜不存在的效果名"的坑。**
这正是剪映 Skill 库的最小同构版：Skill = 参数 schema + 执行映射 + 给 LLM 的说明书。

**再补五个技能**（每个都是"注册表 + 编译器翻译 + 提示词"一次落地）：
1. `delogo` 去水印（最快，纯 ffmpeg）
2. `bgm` 背景音乐轨（amix/acrossfade，顺手修掉 v2.1 的转场音频硬切）
3. `subtitles` ASR 字幕（引入 faster-whisper，唯一新依赖）
4. `trim_silence` 剪静音（先做 silencedetect 信号，零成本）
5. `auto_xfade` 场景切点自动转场（先做场景切分信号，零成本）

**Skill 的能力边界：注册表是漏斗，不是墙**（2026-09-15 讨论定稿）

针对"注册太多 Skill 反而限制 LLM、漏注册就用不了 ffmpeg 能力"的质疑，结论是三层结构：

| 层 | 覆盖 | 机制 | 可靠性 |
|---|---|---|---|
| ① 契约路径 | 高频脏活（上表约 15 个 Skill） | 结构化参数 → 编译器翻译 | 零幻觉、全参数校验、可回验 |
| ② 逃生舱 `custom_filter` | 长尾 ffmpeg 能力 | LLM 直接写滤镜串，过四道闸 | 能跑通，但不背质量保证 |
| ③ 沉淀漏斗 | — | 反复使用且验证稳定 → 升级为注册 Skill | 上限不断变成下限 |

逃生舱的四道闸：
1. **dry-run 语法预检** —— `ffmpeg -t 0.1 -f lavfi -i color=black:s=320x240 -vf "<候选链>" -f null -`
2. **沙箱约束** —— 禁写文件类、破坏性、超长耗时滤镜
3. **显式标记** —— 检视面板标「未验证滤镜」，用户知情
4. **失败回传重试** —— 复用 MAX_RETRIES 通道

没有第 ③ 层，逃生舱会退化成垃圾堆积场——所有脏活都堆在"未验证"路径里，契约路径形同虚设。
**漏斗的方向永远是：逃生舱是 Skill 的候补队列，不是终点。**

**为什么不做全开放**：2026-09-11 的 mirror 坑证明，在**仅 5 个已知 effect** 的能力面下
模型仍会幻觉出不存在的能力名（README 示例"水平镜像" → 模型猜 `{"name":"mirror"}`，
正确应为 `hflip`，被 plan_schema 拦下）；给它 300+ 滤镜的自由空间，幻觉率只会更高。
且剪映 / 时刻Pro / Giga / ICE 无一例外都选择受控能力面，没有先例支持全开放。

**渐进式校验与失败回传**（2026-09-15 讨论定稿）

校验按"由便宜到贵"三层排布，每层失败都带结构化错误回传 LLM：

| 层 | 成本 | 检查内容 | 现状 |
|---|---|---|---|
| ① 静态 schema 校验 | 0 成本 / 毫秒级 | 效果名白名单、参数范围、时间轴数学 | ✅ 已有 |
| ② dry-run 语法预检 | 秒级 | filtergraph 能否被 ffmpeg 解析（按 detect / normalize / render 三段分别预检，便于定位） | 需新增 |
| ③ 真实渲染 + ffprobe 回验 | 分钟级 | 时长 / 分辨率 / 帧率断言 | ✅ 已有 |

**回传错误必须"可定位、可操作"**，带 plan JSON 节点路径：

> `clip[2].effects[0].name='mirror'` 不在可用列表 [hflip, vflip, transpose, eq, face_mosaic]；水平镜像应为 `hflip`

这样 LLM 只改那一个节点，避免"一个错误名导致整个计划重写"从而引入新错误。

- **错误分类**：可自动修复（滤镜名错、参数越界）才重试；不可修复（素材损坏、磁盘满）
  直接报错退出，不浪费重试次数。
- **重试耗尽后显式降级或显式失败**（"第 3 项效果未能实现，已按最小可用版本出片"），
  **绝不静默漏执行**——这正是剪映实测"组合指令只执行一两项且不提示"的坑，我们反向做。

**校验挂载在什么位置：工具 vs 钩子**

检查的锚点不是"LLM 的每一次输出"（大量输出是自然语言推理，没有可校验内容），
而是**结构化产物产生的那一刻**（工具调用参数、计划提交）：

| 形态 | 触发 | 职责 |
|---|---|---|
| `submit_plan`（已有） | LLM 主动提交，完成任务必经之路 | **强制关卡**：所有计划必过校验，错误经 tool result 回传 LLM |
| `validate_plan`（新增） | LLM 主动调用 | **预检**：试算参数、试运滤镜串，把重试轮数从 2 降到 0 |
| middleware 钩子（新增） | 框架自动拦截 | ① 自动纠正建议 ② 统计告警（触发固化漏斗判定）③ 危险滤镜拦截 |

**不做静默自动纠正**：mirror→hflip 纠对了，换个场景可能把 hflip 纠成 vflip——
**错误被藏起来比报出来更糟**。永远"显式报错 + 给出建议"，改了什么也留在日志里。

**信号分析结果必须缓存**（学时刻Pro"上传即索引"）：
场景切分、静音区间跑一次就存进素材的 sidecar 文件（`TMP/probe/<hash>.json`），
同一个素材第二次用不重跑。probe_media 返回的"内容卡片"第一版就是这两项
**——内容理解（原 P0-1）按脏活需要裁剪，只做 L1 信号层，VLM 语义打标后置。**

### R2 · 小白体验：参数卡片回改 + 一键多规格

- **计划回改的小白形态**（原 P0-2 调整）：小白不该看到 JSON 编辑器。
  检视面板把 plan 渲染成**参数卡片**（每个 clip 一张：改 trim 点滑条、换转场类型下拉框、
  调 BGM 音量），点"重新编译"直接走 plan_compiler，**不回 LLM**。
  这是剪映"动态草稿协议"的最小实现：AI 出初稿，确定性系统承接迭代。
- **多规格一键输出**：`output.variants` 数组，横竖方一次渲染（ICE 已验证价值）。
- **示例任务引导**：Web 首页放"去水印 / 加字幕 / 打码 / 拼接"四个任务模板按钮，
  小白点按钮填参数即可，不用会写需求描述。

### R3 · 质量兜底：程序化审阅报告（差异化壁垒）

小白**不会检查成品**——这是他们和 36氪测评作者的本质区别。
所以质量兜底必须由系统做，渲染完成自动出审阅卡片：

| 检查项 | 方法 | 成本 |
|---|---|---|
| 黑帧/纯色帧 | 帧直方图 | 低 |
| 静音段残留 | 复用 silencedetect | 零 |
| 打码覆盖率 | 对照 detect 阶段框数 | 已有 |
| 时长/分辨率/帧率断言 | ffprobe | 已有 |
| 字幕轴完整性 | ASR 时间戳 vs 烧录结果 | 低 |

卖点一句话：**"生成快，审核也快"——直接打剪映实测最大的痛点。**
这些检查项我们自测时全部手写过（A/B 对照渲染、逐帧 diff），
只差从"排障脚本"变成"流水线的一步"。

## 四、明确不做（Scope Guard）

| 不做 | 原因 |
|---|---|
| AI 消除式去水印（inpainting） | 视觉生成模型，效果/成本比 delogo 差，非小白刚需 |
| 自动选曲/音乐推荐 | 是推荐系统不是剪辑；用户指定 BGM 文件即可 |
| 创意叙事/情绪递进编排 | 剪映有 10 亿用户和 Seedance 底模都只做到"模板感"，我们不碰 60 分以上地带 |
| GUI 轨道编辑器 | 产物定位是"能直接发的成品 + 可回改的计划"，不做草稿生态 |
| 多智能体分工（导演/剪辑/审） | 单计划 + 编译器 + 程序化审阅已覆盖需求；为拆而拆是空中楼阁 |

## 五、验收指标（学时刻Pro选北极星）

时刻Pro 用"导出率 50%→60%"和"83% 直接分享"证明价值，我们对应：

| 指标 | 定义 | 目标 |
|---|---|---|
| **一次通过率** | 用户不回改、直接接受成片的任务占比 | ≥ 70% |
| **显式报错率** | 组合指令中漏项/越界被编译器显式报出的比例 | 100%（架构保证） |
| **审阅零遗漏** | 成品带质量报告且无未解释的黑帧/静音 | 100% |
| **复用零重算** | 同一素材第二次任务不重跑信号分析 | 100%（sidecar 缓存） |

## 七、落地顺序建议

```
第 1 步  Skill 注册表地基 + delogo + bgm          （纯 ffmpeg，零新依赖）
第 2 步  校验机制补完：静态错误结构化 + dry-run 预检
         + validate_plan + custom_filter 逃生舱     （保证第 1 步起就"错得看得见"）
第 3 步  静音/场景切分信号 + sidecar 缓存           （零成本信号，解锁后两项）
第 4 步  trim_silence + auto_xfade                （消费上一步的信号）
第 5 步  subtitles（faster-whisper，唯一新依赖）    （装进项目 .venv）
第 6 步  middleware 钩子（纠正建议/统计告警/危险拦截）
第 7 步  参数卡片回改 + variants 多规格             （Web 端）
第 8 步  审阅报告卡片                               （把自测脚本产品化）
```

每一步交付后 SmartTrimAgent 都比上一步多接一类真实的"帮我干脏活"需求，
且始终不偏离"LLM 出意图、编译器保正确"的既有骨架。

  **实现要点（2026-09-17 澄清）**：它是一条**普通 VF 类 Skill**——`build()` 直接把 `args.vf`
  并进滤镜链即可，编译器无需任何特殊逻辑，复用的就是既有的 `_effects_to_vf()` 拼接。

  "本效果会缩放时长" 的标记，由编译器在推导阶段修正 `d_i` / `D`。
