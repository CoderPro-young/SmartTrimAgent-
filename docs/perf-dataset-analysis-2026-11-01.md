## 瓶颈排序（按对总耗时的影响）

### B1｜VLM 打标冷启动——单文件 16.9 分钟，且双路重复烧（最大头，仅冷启动）

冷启动 t1 的 1768.8s 里，**analyze_media 占 1457s（82%）**；63a156（87s 素材）的预热报告单独看更赤裸：

- 预热总 1011s：6 批 VLM 里 **2 批各挂 978s 后失败**、2 批 429s/494s 成功、2 批 1s 秒败；
- 任务内 `analyze_media` 因 sidecar 未落盘**把同一素材又完整跑了一遍（1457s）**——双路挤兑的实时再现：预热 4 路 + 任务内 4 路 = 8 路并发撞 429（`OpenAIRateLimitError` 实录 ×2）；
- 最慢单笔请求：**input 仅 2166 tokens，output 烧到 63,370 tokens（961s）**——GLM-4.5V thinking 预算失控的画像（台账已知：max_tokens 管不住 thinking）。

**优化方向（按预期收益）**：① `enable_thinking:false`（单批 978s → 15~30s 基线，一招砍掉 95%）；② 预热与任务内共享在途分析（任务内等预热落盘而不是重算）；③ 打标并发 4→2 避开 429。三者落地后冷启动 t1 预计 1769s → **~350s**。
**卡片缓存命中率 = 新任务速度第一杠杆**：热重放同任务 291s（-84%）。

### B2｜Agent 大工具轮：20~30s/笔，prompt 2.7万~4.7万字符

热重放两轮的 LLM 全部健康（TTFT 均 ~1s，排队不存在），耗时全在生成；慢笔集中在
18.8k/33.5k/46.9k 字符的大 prompt（27s/20s/26s）。失败轮（14:08）单笔 292s（32.6k 字符
prompt → 16k chunks 长输出）。修订轮 prompt 随轮次膨胀（28k→33k）。

**优化方向**：阶段2 已立项的上下文瘦身（素材卡片摘要化、brief 精简）+ thinking 预算封顶。

### B3｜一键成片宏的 LLM 调用次数：热启动 24 次/244s

旁白、逐镜文案、BGM 挑选等 LLM 调用串行藏在 `compile_expand` 里，TTFT 都健康、纯生成耗时。
**优化方向**：prompt 合并（旁白+文案一次出）、或文案类调用换更快的小模型；并行无依赖调用。

### B4｜渲染段：有界、可忽略级别的工程问题

final 渲染 30.9s（48s 成片）、16.5s（32s 成片）；人脸 detect 8.6s（python 推理 66.6s 是
预览素材 mosaic 案例）；precheck/verify/compile 全部 <1s。调整环已有预览档覆盖，
final 渲染是交付硬成本，暂无必要动。

### B5｜编译与周边环节：全部趋近 0

compile_plan 全子阶段、plan_diff、verify、commit 均 <0.1s——链路里没有隐藏的 CPU 热点，
优化火力应全部集中在 LLM/VLM 请求层。

## 一句话结论

> **热稳态下 84% 的时间在等 LLM 生成（次数 × prompt 体量），冷启动下 82% 在等 VLM 打标
> （thinking 失控 + 双路重算 + 429）。** 第一优先级是 VLM `enable_thinking:false` +
> 双路共享在途分析；第二优先级是阶段2 的上下文瘦身。
