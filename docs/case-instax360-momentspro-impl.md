## 一、产品定位与终极目标

影石把这件事的终局叫 **Camera Man（摄影机器人）**——"用户只管拍摄，不需要做任何剪辑"。
时刻Pro 是这条链路的**最后一步**，前面还有三步（官方称"无感创作四步曲"）：

| 步骤 | 内容 | 关键点 |
|---|---|---|
| ① 无感记录 | 多形态硬件（运动/拇指/全景/无人机） | 从第一人称到上帝视角 |
| ② 无感上云 | 拍摄后 Wi-Fi 自动同步 | 免手动导盘 |
| ③ AI 无感制作 | 多模态 AI 自动筛选成片 | "一键成片" |
| ④ **私人剪辑师** | **时刻Pro**：对话式定制剪辑 | 本文主角 |

✅ 官方强调的护城河：**硬件前置链路**。全景相机"先拍摄后构图"给后期留创作自由度；
运动相机在滑雪/潜水等垂直场景的独特视角数据，让高光识别更准。纯软件产品没有这部分。

## 二、端云双轨：两套完全不同的 AI

同一台 X6 上有两个剪辑 AI，分工是官方明确定义的：

| 维度 | AI 导演（端侧） | 时刻Pro（云端） |
|---|---|---|
| 运行位置 | 相机本地，**不上传云端**，可关闭 | 云端 Agent |
| 触发 | 插电充电至 80% 后自动分析当天素材 | 用户自然语言主动提出需求 |
| 底层 | 自研 PanoMind（30+ 场景、1 万小时专项数据、360° 原生多模态） | 云端多模型（国内 Bedrock 系 / 海外版与 Google Gemini 合作） |
| 产品语义 | "**系统替我选**" | "**按我的想法创作**" |
| 硬件依托 | 4nm AI 三芯：算力 +500%、功耗 -35% | — |

✅ 官方对端侧的说明很关键：分析**全程在相机内完成**，不上云，用户可关闭。
🔶 这解释了为什么端侧只做"高光精选"——它算力有限，只能跑轻量模型做确定性判断；
而语义级理解（"找有小孩的镜头"）放到云端。

✅ 区域差异提示：国内宣传口径强调 Bedrock 多模型，海外评测明确写 "built with Google Gemini"。
大概率是双轨，消费时注意区分。

## 三、核心机制：素材索引（重点）

### 3.1 一句话原理

**把"看视频"变成"建索引"。** 类比搜索引擎：爬虫阶段抓网页、建倒排索引，
搜索时只查索引不重读网页。时刻Pro 的"索引"就是一个个**镜头卡片**。

✅ 官方原话（亚马逊云科技峰会专访）："素材先资产化——海量云端素材提取向量化数据，
沉淀高光评判标准，大模型基于它理解素材内容与创作意图，再做检索/编排/配乐。"
✅ 数据层用的服务也点名了：**Amazon S3 Vectors + Amazon OpenSearch + RAG**。

### 3.2 关键设计：重活前置到"入库那一刻"

这是 1 分钟出片的全部秘密：

| | 入库即索引（影石做法） | 查询时现分析（反面） |
|---|---|---|
| 分析时机 | 素材上云后由后台流水线跑一次 | 用户说话后才开始分析 |
| 查询耗时 | **只做检索 + 排序，亚秒级** | 要跑完整套模型，分钟级起 |
| 重复素材 | 不重算（索引已存在） | 每次都重算 |
| 代价 | 需要常驻的分析算力和存储 | 省存储，但体验差 |

### 3.3 索引单位：镜头卡片

🔶 推断的最小分析单位不是"整个素材"，而是**镜头/场景片段**。
一个素材被切成 N 张卡片，每张卡片长这样（字段为推断，能力来源见标注）：

```
镜头卡片（一条索引记录）
├─ 时间区间      [t_start, t_end]          例：00:12–00:18
├─ 所属素材 ID   source_id
├─ 语义标签      小孩 · 沙滩 · 奔跑 · 笑容      ← ✅ Qwen-VL 类多模态模型
├─ 语义向量      768 维 embedding             ← ✅ "向量化数据"（官方口径）
├─ 人脸 ID 列表  [kid_01, mom_02]            ← ✅ 官方提到"脸部辨识"
├─ 音频特征      笑声 · 人声 · 音乐            ← 🔶 推断（ASR + 声音事件）
├─ 高光分        0.86                        ← ✅ "高光评判标准"（官方口径）
└─ 质量指标      清晰度 / 稳定性 / 构图        ← 🔶 推断
```

**为什么必须切到镜头粒度**：用户最终要的是"剪哪几段"，检索命中必须直接对应
**可剪的时间区间**。如果整个素材只有一个标签，命中后还得再切一次，等于没索引。

### 3.4 三类分析的并行结构

🔶 推断为三条并行线（官方只披露了"多模型协同"和"高光标准"，未披露流水线结构）：

| 分析线 | 做什么 | 技术选型（🔶） |
|---|---|---|
| **视觉语义** | 每个镜头抽关键帧 → 生成场景/物体/动作/情绪标签 + 语义向量 | 多模态 VLM（官方点名 Qwen-VL 在内的多模型） |
| **人脸** | 检测 → 特征提取 → **跨素材聚类**成人物 ID；支持下"设定主角" | 检测 + 人脸特征 embedding + 聚类（官方确认有脸部辨识/设定主角） |
| **音频** | 转写台词、识别声音事件（笑/掌声/音乐/环境音） | ASR + 声学事件分类（🔶） |

**高光评分单独说**：✅ 官方明确说这是**沉淀下来的评判标准**，不是每次现算的通用模型。
它来自 PanoMind 那 1 万小时、30+ 场景的专项数据。这是"数据资产"而非"模型能力"——
也是新入局者最难复制的部分。

### 3.5 存储与检索

✅ 官方点名：S3 Vectors（向量存储）+ OpenSearch（结构化检索）+ RAG。
🔶 推断为**混合检索**：结构化字段（时间、人脸 ID、时长）走 OpenSearch 做硬过滤，
语义向量走 S3 Vectors 做近邻召回，两路结果融合。

## 四、查询链路全走一遍

以用户说 **"剪辑我与孩子一起的时刻"** 为例：

### 4.1 意图解析（LLM / Kiro Agent）

拆成结构化查询：主体 = 孩子、时间范围 = 未指定、风格 = 默认、输出 = 平台默认规格。

⚠️ **这里有个容易被忽略的难点：指代消解。**
"**我的**孩子"里的"我"，系统并不认识。除非用户做过**主角绑定**——
✅ 这正是官方提到"脸部辨识/设定主角"的原因：用户事先标注"这是我家孩子"，
`kid_01` 才和"我的孩子"这个词建立映射。**没有这一步，语义检索会退化成泛化的"小孩"。**

### 4.2 双通道召回

| 通道 | 依据 | 特点 |
|---|---|---|
| **结构通道** | 人脸 ID 精确过滤（`kid_01` 出现的镜头） | 精确、可解释、依赖用户标注过主角 |
| **语义通道** | query 向量 × 卡片语义向量的近邻检索 | 兜底，用户没标注主角也能召回"小孩"相关镜头 |

🔶 双通道是推断，但它解释了官方"87% 成功率"的鲁棒性来源——
两条路互补，不依赖单点。

### 4.3 融合排序

🔶 推断打分要素：人脸命中（权重最高）→ 高光分 → 时长与时间范围约束 → 去重（同场景留最佳）。
输出候选池（一批可剪的时间区间）。

### 4.4 编排与渲染

- LLM 把候选排成叙事顺序
- 配乐（按情绪标签选）、转场、平台规格适配（9:16 等）
- ✅ 云端并发渲染：**100 并发任务 30 分钟 → 1 分钟**（Bedrock AgentCore 的功劳）
- 成品推送到 App

## 五、关键设计决策分析

### 5.1 为什么"孩子"这个需求特别值得研究

**"孩子"不是物体标签，是人物实体。**

- 如果只是物体检测："小孩"这类标签匹配就够了
- 但用户要的是"**我**的孩子"——同一个孩子在几千个镜头里出现，
  必须靠**跨素材人脸聚类**把他连成一个可查询的实体

这比物体检测难，也明显更值钱。它是那 87% 成功率里最硬的一块。

### 5.2 为什么端侧做不了这件事

端侧只做"高光精选"（确定性判断：清晰度、稳定性、运动能量），
不做语义理解（"有没有小孩"）。原因：**端侧算力有限 + 语义模型跑不动**。
这就是为什么必须有云端时刻Pro——端云分工不是产品噱头，是算力约束的必然。

### 5.3 北极星指标的选择

✅ 官方用**导出率**而非"生成速度"证明价值：2026 Q1 达 50%，Q2 提升至 60%；
83% 的导出视频直接分享到社交平台。

**解读**：用户对"拿到能直接发的东西"付费，而不是对"拿到一个工程文件"付费。
这个指标选择本身值得学。

## 七、对 SmartTrimAgent 的映射

| 时刻Pro 的做法 | 我们对应 | 差距 |
|---|---|---|
| 入库即索引 + sidecar 缓存 | 已在 roadmap T11 规划 | 未实现 |
| 人脸检测 | ✅ 已有（YuNet） | — |
| 人脸**聚类成实体** | ❌ 无 | 缺聚类 + 主角标注入口 |
| 语义标签 + 向量 | ❌ 无（VLM 后置） | 按定位暂不做 |
| 高光评判标准沉淀 | ❌ 无 | 长期资产，非近期 |
| 跨素材检索 | ❌ 无（单次任务内） | 缺素材库概念 |

**最小可行的"找小孩"版本**（不引入 VLM）：
用户在 Web 标一张孩子照片 → YuNet 逐帧检测 → 与参照脸做相似度比对 → 命中的镜头进候选池。
技术上完全可行，但**按"脏活自动化"定位属于远期 P3**——"找有小孩的镜头"是创作型需求，
不在脏活清单里，做不做取决于是否要往"智能选择"方向伸。
