## §1 VLM 打标 429 限流拖慢新任务（2026-10-30 晨）——**未修**

### 现象

用户 09:25:43 / 09:26:03 先后上传两个微信视频（文件名时间戳），~09:26:49
提交一键成片任务，前端转圈 15 分钟+ 无进展，`/api/health` 一直 busy。

### 证据（LangSmith 轨迹 + /api/inputs）

| 时刻 | 调用 | 耗时 |
|---|---|---|
| 09:26:50~09:27:05 | 主模型 DeepSeek-V4-Flash ×3 | 3s / 5s / 36s——**全部正常** |
| 09:26:47 | VLM GLM-4.5V | **193s**（正常 15~30s/批） |
| 09:26:49 | VLM GLM-4.5V | **RUNNING 14 分钟+ 未返回** |
| 09:27:09 | VLM GLM-4.5V | **RUNNING 13 分钟+ 未返回** |
| 09:27:05 / 09:30:00 | VLM GLM-4.5V | 36s / 47s |

`/api/inputs`：素材 #3 打标完成（ready），**素材 #4 卡在 analyzing**；
agent 在工具节点同步等 `analyze_media(#4)` 返回——打标不回，整条管线
看似死锁，实际活着（LangSmith 可见 RUNNING）。

**结局**：#4 打标完成后任务自行走完，09:45 出片
（`OUTPUT/concert_highlight-r2-r3.mp4`，17MB + EDL/CSV）。
端到端 ~18 分钟（09:26:49 提交 → 09:45 完成），其中打标等待占 ~15 分钟，
与诊断一致——纯等待，无工作量。

### 根因

1. **SiliconFlow GLM-4.5V 有 TPM 限流**，打标是多帧并发批量请求，超限即
   429 退避。2026-10-29 已实测过同画像（8 路并发打爆 TPM，单笔被拉长到
   8~13 分钟）；本次单笔 193s~14min+ 再次确认。
2. **双路挤兑放大**：上传即触发后台索引（8 路并发线程池），用户随即点
   运行，agent 又在线程内同步调 `analyze_media` 建卡——两路对同一配额
   各打各的，退避更长。
3. **10-28 超时治理的盲区（本次新证据）**：VLM 工厂实际生效参数是
   `VLM_TIMEOUT=60`（流式）+ `VLM_RETRIES=1`（`.env` 无覆盖），单笔
   理论上限 ~125s；但有单笔 RUNNING 超 14 分钟没被掐断。流式 read
   timeout 只掐「静默」——被限流的请求若以细流/重试方式拖延（每个字节
   都重置 60s 计时器，或 SDK 层按 Retry-After 反复等待），闸门形同虚设。
   **机制待 HTTP 层取证**（LangSmith 只能看到「单笔未返回」，看不到
   内部是慢流还是重试循环）。

### 影响

- 首轮创作对未索引素材的等待 ≈ 打标时长，受限时 10 分钟+；期间前端只有
  心跳，无「在等打标」的进展语义。
- 与请求挂死（10-28 已治）不同：这类等待是「合法但被限流拖长」，客户端
  掐得再狠也只是早失败，不解决问题。

### 优化方向（按预期收益排，均未动工）

1. **后台索引与线程内 analyze_media 合流去重**：同素材已有在途分析时，
   线程内调用复用同一 job 等它完成（进度钩子已有先例），而不是两路各打
   各的配额。纯结构改动，不碰供应商。
2. **打标并发限流 8→2~3 路**：TPM 之内 429 消失，总吞吐反而可能更高
   （退避不再指数膨胀）。改 content_analysis 线程池参数即可。
3. **前端进展语义**：素材未 ready 时「运行」按钮提示「内容索引中，稍等
   更快」（analysis 事件通道已有），避免用户在打标期提交、再误以为卡死。
4. **每素材抽帧数上限/降采样**：减少单素材的打标批次数（与 2 叠加）。
5. （关联 10-28 文档遗留项）内容卡缓存键从 mtime 改 content hash，
   避免素材挪动即 944s 全量重分析。
6. **观察项**：流式闸门对「细流型拖延」失效——若后续主模型也出现同类
   长尾，考虑给逻辑调用加「总时长墙」（超墙即失败重试，宁可早败不可
   陪等）；先取证再动。
