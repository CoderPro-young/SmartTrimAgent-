SmartTrimAgent 后续改进方向 —— 脏活自动化 × 小白快速出片

2026-09-13 ｜ 基于《案例对比报告》《时刻Pro/剪映补充深挖》与定位讨论收敛而成。 定位一句话：不帮用户生成高创意内容；帮新手小白和刚接触剪辑的人快速出"能用"的片， 把去水印、加字幕、配 BGM、转场、打码这类脏活粗活累活全部自动化。

一、为什么这个定位成立（两个 case 的交叉论证）

剪映的 68 分实测恰好是定位合理性的证明。 36氪测评的结论是"效率拉高几倍，但只能从 0 做到 60 分，不懂情绪递进、模板感重"。 注意：这个批评对专业创作者是缺点，对小白恰恰是够用的——小白要的就是 "快速得到一个结构完整、节奏规整、挑不出毛病的及格片"。剪映 10 亿用户盘子里， 最大的群体本来就是这个需求。我们不碰它"高光 60 分以上"的地带，只做 0→60 这一段。

Avid 的行业调研给这个定位背书。 79% 职业剪辑师已在用 AI，最高频用途是语音转文字（60%），87% 认为 AI 的价值在于 "更高效地实现自己的意图"——连专业用户都优先把 AI 用在脏活上，小白更是如此。

时刻Pro证明"快速出片"本身就是一个完整产品。 87% 自然语言成功率、2025 年 1.2 亿条、83% 导出后直接分享——用户付费的就是 "拿到能直接发的东西"。它没有试图做创意表达（那是 PanoMind 端侧高光精选的事）， 云端时刻Pro 的卖点就是"一分钟出能用的片"。

我们的差异化：剪映的两个实测坑，恰好是我们架构的原生强项。

剪映实测问题根因我们的对应机制
组合指令常漏执行一两项命令式架构：子 Agent 各干各的，无全局合成层声明式计划 JSON：编译器统一校验，漏项/越界显式报错
"生成快、审核慢"，配错画面不提示无程序化质量门禁，审核转嫁给用户ffprobe 回验 + 程序化审阅报告（见 R3），审核也快

三、路线：三个阶段

R1 · 能力面：Skill 注册表 + 补齐五个脏活（最优先）

先修地基——Skill 注册表（原 P1-1 提级为 R1 首项）：

SKILLS = {
  "delogo":       Skill(args_schema={...}, to_vf=..., prompt_doc=...),
  "subtitles":    Skill(args_schema={...}, to_vf=..., prompt_doc=...),
  "bgm":          Skill(args_schema={...}, to_af=..., prompt_doc=...),
  "auto_xfade":   Skill(args_schema={...}, needs=["scene_cuts"], to_filter=..., ...),
  "trim_silence": Skill(args_schema={...}, needs=["silence_ranges"], ...),
  "face_mosaic":  Skill(...),  # 现有能力迁入
}

schema 校验、命令生成、提示词文档全部从注册表派生—— 一处定义同时消灭"新增 effect 同步三处"的坑和"模型猜不存在的效果名"的坑。 这正是剪映 Skill 库的最小同构版：Skill = 参数 schema + 执行映射 + 给 LLM 的说明书。

再补五个技能（每个都是"注册表 + 编译器翻译 + 提示词"一次落地）：

  1. delogo 去水印（最快，纯 ffmpeg）
  2. bgm 背景音乐轨（amix/acrossfade，顺手修掉 v2.1 的转场音频硬切）
  3. subtitles ASR 字幕（引入 faster-whisper，唯一新依赖）
  4. trim_silence 剪静音（先做 silencedetect 信号，零成本）
  5. auto_xfade 场景切点自动转场（先做场景切分信号，零成本）

Skill 的能力边界：注册表是漏斗，不是墙（2026-09-15 讨论定稿）

针对"注册太多 Skill 反而限制 LLM、漏注册就用不了 ffmpeg 能力"的质疑，结论是三层结构：

层覆盖机制可靠性
① 契约路径高频脏活（上表约 15 个 Skill）结构化参数 → 编译器翻译零幻觉、全参数校验、可回验
② 逃生舱 custom_filter长尾 ffmpeg 能力LLM 直接写滤镜串，过四道闸能跑通，但不背质量保证
③ 沉淀漏斗—反复使用且验证稳定 → 升级为注册 Skill上限不断变成下限

逃生舱的四道闸：

  1. dry-run 语法预检 —— ffmpeg -t 0.1 -f lavfi -i color=black:s=320x240 -vf "<候选链>" -f null -
  2. 沙箱约束 —— 禁写文件类、破坏性、超长耗时滤镜
  3. 显式标记 —— 检视面板标「未验证滤镜」，用户知情
  4. 失败回传重试 —— 复用 MAX_RETRIES 通道

没有第 ③ 层，逃生舱会退化成垃圾堆积场——所有脏活都堆在"未验证"路径里，契约路径形同虚设。 漏斗的方向永远是：逃生舱是 Skill 的候补队列，不是终点。

为什么不做全开放：2026-09-11 的 mirror 坑证明，在仅 5 个已知 effect 的能力面下 模型仍会幻觉出不存在的能力名（README 示例"水平镜像" → 模型猜 {"name":"mirror"}， 正确应为 hflip，被 plan_schema 拦下）；给它 300+ 滤镜的自由空间，幻觉率只会更高。 且剪映 / 时刻Pro / Giga / ICE 无一例外都选择受控能力面，没有先例支持全开放。

渐进式校验与失败回传（2026-09-15 讨论定稿）

校验按"由便宜到贵"三层排布，每层失败都带结构化错误回传 LLM：

层成本检查内容现状
① 静态 schema 校验0 成本 / 毫秒级效果名白名单、参数范围、时间轴数学✅ 已有
② dry-run 语法预检秒级filtergraph 能否被 ffmpeg 解析（按 detect / normalize / render 三段分别预检，便于定位）需新增
③ 真实渲染 + ffprobe 回验分钟级时长 / 分辨率 / 帧率断言✅ 已有

回传错误必须"可定位、可操作"，带 plan JSON 节点路径：

clip[2].effects[0].name='mirror' 不在可用列表 [hflip, vflip, transpose, eq, face_mosaic]；水平镜像应为 hflip

这样 LLM 只改那一个节点，避免"一个错误名导致整个计划重写"从而引入新错误。

  • 错误分类：可自动修复（滤镜名错、参数越界）才重试；不可修复（素材损坏、磁盘满）

直接报错退出，不浪费重试次数。

  • 重试耗尽后显式降级或显式失败（"第 3 项效果未能实现，已按最小可用版本出片"），

绝不静默漏执行——这正是剪映实测"组合指令只执行一两项且不提示"的坑，我们反向做。

校验挂载在什么位置：工具 vs 钩子

检查的锚点不是"LLM 的每一次输出"（大量输出是自然语言推理，没有可校验内容）， 而是结构化产物产生的那一刻（工具调用参数、计划提交）：

形态触发职责
submit_plan（已有）LLM 主动提交，完成任务必经之路强制关卡：所有计划必过校验，错误经 tool result 回传 LLM
validate_plan（新增）LLM 主动调用预检：试算参数、试运滤镜串，把重试轮数从 2 降到 0
middleware 钩子（新增）框架自动拦截① 自动纠正建议 ② 统计告警（触发固化漏斗判定）③ 危险滤镜拦截

不做静默自动纠正：mirror→hflip 纠对了，换个场景可能把 hflip 纠成 vflip—— 错误被藏起来比报出来更糟。永远"显式报错 + 给出建议"，改了什么也留在日志里。

信号分析结果必须缓存（学时刻Pro"上传即索引"）： 场景切分、静音区间跑一次就存进素材的 sidecar 文件（TMP/probe/<hash>.json）， 同一个素材第二次用不重跑。probe_media 返回的"内容卡片"第一版就是这两项 ——内容理解（原 P0-1）按脏活需要裁剪，只做 L1 信号层，VLM 语义打标后置。

R2 · 小白体验：参数卡片回改 + 一键多规格

  • 计划回改的小白形态（原 P0-2 调整）：小白不该看到 JSON 编辑器。

检视面板把 plan 渲染成参数卡片（每个 clip 一张：改 trim 点滑条、换转场类型下拉框、 调 BGM 音量），点"重新编译"直接走 plan_compiler，不回 LLM。 这是剪映"动态草稿协议"的最小实现：AI 出初稿，确定性系统承接迭代。

  • 多规格一键输出：output.variants 数组，横竖方一次渲染（ICE 已验证价值）。
  • 示例任务引导：Web 首页放"去水印 / 加字幕 / 打码 / 拼接"四个任务模板按钮，

小白点按钮填参数即可，不用会写需求描述。

R3 · 质量兜底：程序化审阅报告（差异化壁垒）

小白不会检查成品——这是他们和 36氪测评作者的本质区别。 所以质量兜底必须由系统做，渲染完成自动出审阅卡片：

检查项方法成本
黑帧/纯色帧帧直方图低
静音段残留复用 silencedetect零
打码覆盖率对照 detect 阶段框数已有
时长/分辨率/帧率断言ffprobe已有
字幕轴完整性ASR 时间戳 vs 烧录结果低

卖点一句话："生成快，审核也快"——直接打剪映实测最大的痛点。 这些检查项我们自测时全部手写过（A/B 对照渲染、逐帧 diff）， 只差从"排障脚本"变成"流水线的一步"。

远期（明确后置，不进近期排期）

  • VLM 语义打标 / "找有小孩的镜头"（时刻Pro L3 路线，接 SiliconFlow vision 模型，按帧配额计费）
  • 高光集锦、多素材智能选择（依赖上一条）
  • user_style 偏好沉淀（时刻Pro"高光评判标准"路线）
  • 叙事规划 Agent（CutClaw 路线，前提是先有内容理解，且与"脏活"定位无关）

七、落地顺序建议

第 1 步  Skill 注册表地基 + delogo + bgm          （纯 ffmpeg，零新依赖）

         + validate_plan + custom_filter 逃生舱     （保证第 1 步起就"错得看得见"）
第 3 步  静音/场景切分信号 + sidecar 缓存           （零成本信号，解锁后两项）

第 8 步  审阅报告卡片                               （把自测脚本产品化）

每一步交付后 SmartTrimAgent 都比上一步多接一类真实的"帮我干脏活"需求， 且始终不偏离"LLM 出意图、编译器保正确"的既有骨架。

实现要点（2026-09-17 澄清）：它是一条普通 VF 类 Skill——build() 直接把 args.vf 并进滤镜链即可，编译器无需任何特殊逻辑，复用的就是既有的 _effects_to_vf() 拼接。 唯一的增量是 dry-run 预检要作为新阶段（precheck）插在「编译完成 → 执行之前」。 ⚠️ 适用边界：只允许 逐帧像素变换（unsharp/gblur/vignette/curves/deband/deshake …）， 不允许改变时序的滤镜（变速 setpts、倒放、抽帧、循环）。原因：编译器按 d = trim_end - trim_start 推导时长并写死 -t d，改变时长的滤镜会让时间轴数学失效 → 成品时长错、音画不同步。变速率能力必须走契约路径注册，并让 Skill 携带 "本效果会缩放时长" 的标记，由编译器在推导阶段修正 d_i / D。

  • [ ] T7b speed 变速技能（契约路径，非逃生舱）：Skill 增加时长缩放标记

（如 time_scale: 1/rate），编译器的 _derive() 据此修正片段时长与总时长； 音频同步用 atempo（可串联，单级限 0.5~2.0）。
