## 1. 需求梳理

用户在 v2 提出的能力（自然语言驱动）：

| 能力 | 用户原话示例 |
|---|---|
| 多素材拼接 | 把某几个素材拼接起来 |
| 按时间点插入 | 在某个素材的第 N 秒… |
| 画中画（PiP） | 加入一个画中画 |
| 花字（文字叠加） | 加一个花字 |
| 裁剪 | 某个视频的前 N 秒剪掉 |
| 转场 | 两个视频结合处做一个转场 |

**核心难点：素材异构性。** 多个素材可能：
- 容器不同：mp4 / avi / mov / 图片（png/jpg）
- 分辨率不同：1080p / 720p / 竖屏
- 编码不同：H.264 / H.265 / VP9 / MJPEG（图片）
- 帧率不同：25 / 30 / 60 fps
- 音频不同：有/无音轨、单声道/立体声、采样率不同

→ **异构流不能直接 `concat`/`xfade`，必须先归一化。**

## 2. 总体架构：归一化中间态 + 结构化编辑计划

```
用户自然语言
   │
   ▼
┌──────────────────────────── 智能层（LLM） ────────────────────────────┐
│  deepagents agent                                                   │
│  ├─ 工具 probe_media(path) → 素材元数据 JSON                         │
│  ├─ 工具 list_inputs() / ls                                          │
│  └─ 输出：结构化「编辑计划 JSON」（含已探测的素材元数据）              │
└────────────────────────────────┬────────────────────────────────────┘
                                 ▼
┌──────────────────────────── 工程层（程序编译） ──────────────────────┐
│  plan_compiler.py                                                   │
│  1. 校验计划（schema + 语义），失败 → 携错误回 LLM 重计划（≤2 次）     │
│  2. 归一化：timeline 素材 → 统一中间格式（复用 LLM 已探测的元数据）     │
│  3. 时间轴换算：xfade offset、overlay enable 时间（§5 公式）           │
│  4. 生成命令序列 → run_ffmpeg 执行 → ffprobe 回验                      │
└──────────────────────────────────────────────────────────────────────┘
                                 ▼
                            OUTPUT/产物
```

关键决策：**LLM 输出「编辑计划」，不直接输出 ffmpeg 命令**。理由：

1. 多素材归一化参数需要基于 probe 结果程序化计算（目标分辨率、是否有音轨、时长换算），LLM 手算易错。
2. `filter_complex` 多输入时间轴（xfade offset 累加、overlay 绝对时间）是确定性数学，交给代码最稳。
3. 计划 JSON 可校验、可回滚、可缓存归一化中间产物；命令直接执行则难以校验。
4. probe 职责澄清：LLM 调 `probe_media` 是为了**做计划决策**（素材多长、能裁多少）；编译器**复用计划里带回的元数据**，不重复探测。

## 3. 归一化中间格式规范（Normalized Intermediate）

**只对进入 timeline 的素材做归一化**；overlay 用的图片不归一化（见 §6）。

| 维度 | 目标值 | 说明 |
|---|---|---|
| 视频编码 | H.264 (libx264) | 兼容性最好 |
| 像素格式 | yuv420p | 必须，否则 concat/xfade 报错 |
| 分辨率 | 统一画布（策略见下） | scale + pad 黑边，保证同画布 |
| 帧率 | 统一 30fps（或用户指定） | 必须 CFR，concat 需要一致 |
| 音频编码 | AAC 128k | 无音轨素材补静音轨（anullsrc） |
| 声道 | 统一 stereo（-ac 2） | 避免通道数不一致 |
| 采样率 | 48000 Hz | 统一 |
| 图片素材 | 转成 N 秒视频片段（-loop 1 -t N，默认 3s 或用户指定） | 图片 → 主轨视频流 |

**画布策略**（review 修订 + 2026-08-22 调研确认）：`用户指定分辨率 > 面积最大素材的原始分辨率`。
不要用"取各素材最大宽×最大高"——横屏 1920×1080 与竖屏 1080×1920 混合会得到 1920×1920 的荒谬画布。

调研结论（ffmpeg 官方教程 + 主流剪辑工具 CapCut/影忆/Flow AI 通行做法），比例不一致时共三种策略：

| 策略 | 做法 | 适用 | 版本 |
|---|---|---|---|
| **pad 黑边（letterbox/pillarbox）** | `scale=W:H:force_original_aspect_ratio=decrease,pad=W:H:(ow-iw)/2:(oh-ih)/2,setsar=1` | ffmpeg 标准做法，保留完整画面，实现最简单 | **v2.0 默认** |
| 背景填充（blur-fill） | 原视频放大模糊作背景（`scale=increase + boxblur`），完整画面居中叠加 | 短视频创作者主流选择，视觉柔和、无黑边割裂感 | v2.1 |
| 裁剪填满（crop-fill） | `crop` 到目标比例（主体识别辅助可选） | 主体集中的素材（人像/产品特写） | v2.1 |

结论：**v2.0 按 pad 黑边实现**（与 ffmpeg 官方多比例拼接教程一致），blur-fill 作为 v2.1 可配置选项加入计划 schema。

归一化命令模板（以 mp4 → 中间 mp4 为例）：

```bash
ffmpeg -y -i INPUT/a.mp4 \
  -vf "scale=1280:720:force_original_aspect_ratio=decrease,pad=1280:720:(ow-iw)/2:(oh-ih)/2,fps=30,format=yuv420p" \
  -c:v libx264 -preset veryfast -crf 18 \
  -c:a aac -b:a 128k -ar 48000 -ac 2 \
  -shortest \
  TMP/a_norm.mp4
```

无音轨素材：先补静音 `-f lavfi -i anullsrc=r=48000:cl=stereo` 再 `-shortest`。
图片素材：`-loop 1 -t 5 -i INPUT/img.png ...`。

## 4. 编辑计划 JSON 模型（LLM 输出）

LLM 输出固定 schema，程序解析校验。核心字段：

```json
{
  "output": {
    "filename": "OUTPUT/final.mp4",
    "resolution": { "width": 1280, "height": 720 },
    "fps": 30
  },
  "clips": [
    { "id": "c1", "source": "INPUT/a.mp4", "trim_start": 5, "trim_end": null,
      "kind": "video", "probe": { "duration": 10.0, "width": 1920, "height": 1080,
                                  "fps": 30, "has_audio": true, "channels": 2 } },
    { "id": "c2", "source": "INPUT/b.avi", "trim_start": 0, "trim_end": 10,
      "kind": "video", "probe": { "duration": 15.0, "width": 1280, "height": 720,
                                  "fps": 25, "has_audio": false } }
  ],
  "timeline": [
    { "clip": "c1" },
    { "clip": "c2", "transition": { "type": "fade", "duration": 0.5 } }
  ],
  "overlays": [
    { "type": "pip", "source": "INPUT/logo.png", "kind": "image",
      "at_clip": "c1", "start_offset": 0.5, "duration": 4,
      "position": "bottom-right", "scale": 0.25 },
    { "type": "pip", "source": "INPUT/clip2.mp4", "kind": "video",
      "at_clip": "c1", "start_offset": 1, "duration": 4,
      "position": "top-right", "scale": 0.25, "mix_audio": false },
    { "type": "text", "text": "你好，世界", "at_clip": "c1", "start_offset": 1,
      "duration": 4, "font_size": 48, "color": "#FFFFFF",
      "position": { "x": "center", "y": "top" } }
  ]
}
```

要点（review 修订处加粗）：
- **`start_offset` 基准 = 裁剪后片段内时间**：0 = 该 clip 进入时间轴的起点。LLM 需把用户的"素材第 N 秒"换算成片段内时间（素材被 trim 过时用户时间可能落在片段外，校验时报错回 LLM 重计划）。
- **clips 只放 timeline 素材**；overlay 的 PiP 源直接引用素材文件（`source` + `kind`），图片不归一化成视频，直接 overlay；视频 PiP 由编译器按 scale 参数现场缩放。
- **`probe` 元数据随计划带回**：编译器复用，不重复探测；LLM 填写前必须先调 `probe_media`。
- **`transition.type` 白名单枚举**：fade / dissolve / wipeleft / wiperight / slideup / slidedown / circleopen / circleclose 等（xfade 支持的子集），校验时拒绝白名单外的值。
- `trim_end` 为 null 表示用素材全长；**校验：`trim_end - trim_start ≤ probe.duration`**。
- 转场挂在 timeline 相邻项之间；校验：`transition.duration < min(相邻两 clip 时长)`。

## 5. 时间轴数学（review 新增，编译器核心）

设 timeline 共 N 个 clip，`d_i` 为第 i 个 clip 裁剪后时长，`t_i` 为第 i 个转场时长（i=2..N，即 clip i 与前一个之间）：

**输出总时长**（xfade 转场有重叠，时长被"吃掉"）：

```
D = Σ d_i − Σ t_i
```

**clip i 在最终时间轴上的起点**：

```
S_1 = 0
S_i = S_(i−1) + d_(i−1) − t_i      （转场与前一段重叠 t_i）
```

**xfade 链式 offset**（第 i 次转场作用在已合并流 `[x_{i-1}]` 与 clip i 之间）：

```
offset_i = S_i                      （即前一段内容开始淡出的时刻）
```

注意：ffmpeg 的 xfade `offset` 定义为"第一个输入开始过渡的时刻"，等于 `S_i`；
`[x_i]` 的总时长 = `S_i + d_i`，后续链式计算以合并流为准。

**overlay 绝对时间换算**（overlay 挂在 `at_clip` + `start_offset`）：

```
enable_start = S_(at_clip) + start_offset
enable_end   = enable_start + duration
校验：enable_end ≤ S_(at_clip) + d_(at_clip)
```

**回验预期**：输出总时长应 ≈ D（±0.5s）；不符报错。

## 6. 两条渲染路径（review 修订：不再混用）

| 路径 | 条件 | 技术 | 成本 |
|---|---|---|---|
| **快速路径** | timeline 无任何转场 | 归一化后 concat demuxer `-c copy` | 极快（无重编码） |
| **转场路径** | timeline 有转场 | filter_complex：链式 xfade + overlay/drawtext，一次重编码 | 慢（全程重编码） |

两路径选择由编译器根据计划自动判定。overlay（画中画/花字）存在时无论哪条路径都需要重编码一次——快速路径退化为"concat 后叠加"，即两步：concat（-c copy）→ overlay 渲染（重编码一次）。

各操作技术要点：

| 操作 | 技术 | 命令要点 |
|---|---|---|
| 拼接（无转场） | concat demuxer | `-f concat -safe 0 -i list.txt -c copy` |
| 裁剪 | 归一化时 `-ss trim_start`（+`-t`） | 计划驱动，不单独出命令 |
| 转场 | xfade 链式 | `xfade=transition=<白名单>:duration=T:offset=<§5 公式>` |
| 画中画 | overlay | `[ovr]scale=W*0.25:-2[p];[base][p]overlay=..:enable='between(t,ts,te)'` |
| 花字 | drawtext | 短文本 `text='...'`；**含特殊字符（冒号/引号）或长文本用 `textfile=TMP/t.txt`**（review 修订） |

示例（2 素材 + fade 转场 + 图片角标；d1=5s，fade 0.5s）：

```bash
# 归一化 a、b → TMP/a_n.mp4、TMP/b_n.mp4（略）
# 转场路径：S_2 = 0 + 5 − 0.5 = 4.5 → offset=4.5
ffmpeg -y -i TMP/a_n.mp4 -i TMP/b_n.mp4 -loop 1 -t 5 -i INPUT/logo.png \
  -filter_complex "\
[0:v][1:v]xfade=transition=fade:duration=0.5:offset=4.5[x0]; \
[2:v]scale=320:-2[ovr]; \
[x0][ovr]overlay=W-w-20:H-h-20:enable='between(t,3,8)'[vout]; \
[0:a][1:a]concat=n=2:v=0:a=1[aout]" \
  -map "[vout]" -map "[aout]" -c:v libx264 -crf 20 -c:a aac OUTPUT/final.mp4
```

**音频行为（review 明确）**：v2.0 转场处音频采用 concat 直接拼接（有轻微跳变，可接受）；
平滑音频交叉淡变（acrossfade）放 v2.1。画中画素材音轨默认不混入（`mix_audio: false`）。

## 8. 错误处理与回验

- 归一化失败 → 报告具体素材 + ffmpeg stderr，中止，不产生半成品。
- 计划校验失败（schema / 时间越界 / 转场时长越界 / 白名单外转场）→ 带错误回 LLM 重计划（≤2 次）。
- 产物回验：ffprobe 检查输出时长 ≈ D（§5 公式，±0.5s）、分辨率/编码符合 `output`；不符报错。
- 缓存：`TMP/` 归一化产物按素材内容哈希命名，重复任务跳过转码。

## 10. 风险与待定项

- **字体文件**：drawtext 中文花字需要字体，Windows 用 `C\:/Windows/Fonts/msyh.ttc`，需确认存在；跨平台要配置。
- **ffprobe 依赖**：v2 强依赖 ffprobe（ffmpeg 同包附带），本机仍未装 ffmpeg，验证停留在「计划 JSON + 生成命令」层，真实渲染需安装 ffmpeg。
- **性能**：转场路径全程重编码 + 归一化一次重编码（两代损失）；归一化 crf 18 尽量保值，大文件耗时靠缓存缓解。
- **xfade 音频**：v2.0 音频硬切，v2.1 acrossfade。
- **overlay 音频**：画中画素材音轨默认不混入；混音需求 v2.1。
- **LLM 计划质量**：DeepSeek-V4-Flash 对复杂 schema 的 JSON 遵循度需实测；备选手段：prompt 内嵌 schema + 示例，校验失败重试，仍失败则降级人工确认。
- **画布策略**：默认 pad 黑边；crop-fill 模式 v2.1。

## 11. 与 v1.0 的关系

v1.0 的「LLM 直接生成 ffmpeg 命令」对单素材简单任务依然可用；v2.0 引入计划层后，
单素材任务也可走统一管线（计划 → 编译），v1.0 的 demo 保留作为对照。

路线图更新：v1.0（单命令）→ **v2.0（多素材剪辑：归一化 + 计划 + 编译）** →
v2.1（音频转场/混音、crop-fill、滤镜模板库）→ v3（命令白名单 + 安全校验 + Web 前端）。

## 12. 扩展性设计（2026-08-22 补充）

**问题**：计划 JSON 是否定制化过强？后续加"视频镜像、翻转、素材左右拼接展示"等能力是否要改 schema？

**结论**：计划层确实是领域定制的（这是可校验、可算时间轴的代价），但扩展不需要每加一个功能改一次
schema——所有新能力落入**三个通用扩展点**，每个扩展点是"白名单 + 编译器映射"，管线的三个阶段
（probe → 归一化 → 渲染）与 §5 时间轴数学保持不变。

### 扩展点一：clip 效果插槽（片段级视觉处理）

clip 上增加 `effects` 数组（白名单枚举），编译进归一化阶段的 `-vf` 链：

```json
{ "id": "c1", "source": "INPUT/a.mp4", "kind": "video",
  "effects": [ { "name": "hflip" }, { "name": "transpose", "args": { "dir": 1 } } ] }
```

→ 归一化时 `-vf "hflip,transpose=1,scale=...,pad=..."`。
白名单初始集：`hflip`（镜像）、`vflip`（垂直翻转）、`transpose`（旋转 90/180/270）、
`eq`（亮度/对比度/饱和度）、`setpts+atempo`（变速）、`crop`（裁剪）、`fade in/out`（淡入淡出）。
新增一种效果 = 白名单加一项 + 编译器加一条 filter 映射。

### 扩展点二：overlay 区域化（任意矩形位叠加）

把 `pip` 的 `position + scale` 泛化为 `region`（画布百分比矩形），一个原语覆盖一类需求：

```json
{ "type": "video", "source": "INPUT/b.mp4", "at_clip": "c1",
  "start_offset": 0, "duration": 5,
  "region": { "x": "50%", "y": 0, "w": "50%", "h": "100%" } }
```

→ `overlay` 按百分比矩形定位。画中画 = 小矩形 + 角位；半屏同框 = 两个半幅矩形；
水印角标、四分屏、多素材同屏展示均由此表达，无需新 schema 结构。

### 扩展点三：timeline 布局块（同屏多素材段）

timeline 条目从"单 clip"泛化为"clip 或 layout 块"。layout 块是一段**多素材同屏**的时间段，
编译器先把各素材归一化并缩放进网格单元（hstack / vstack / xstack），拼成一段普通视频后进时间轴，
与转场/时间轴数学完全兼容：

```json
"timeline": [
  { "clip": "c1" },
  { "layout": { "type": "grid", "cols": 2, "clips": ["c2", "c3"], "duration": 8 },
    "transition": { "type": "fade", "duration": 0.5 } },
  { "clip": "c4" }
]
```

→ 左右拼接（1×2 网格）、上下拼接（2×1）、九宫格（3×3）都是 `grid` 的参数化。
layout 段的时长 = `duration`（各素材循环/截断对齐到该时长），S/D 公式照常适用。

### 演进与兜底

- 计划根字段加 `"schema_version": "2.0"`：编译器按版本分发解析，向后兼容演进。
- 真正奇异的、白名单表达不了的需求（极少数）：回退 v1 的「LLM 直生成 ffmpeg 命令 + 人工确认」
  逃生舱，不阻塞主链路。
- 已知代价：每类新能力仍需编译器实现一条确定性映射——这是「计划编译」架构的固有成本，
  换来的是可校验、可回验、时间轴不出错。
