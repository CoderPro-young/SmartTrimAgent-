# 开发纪要 2026-10-28：V10 计划工具化——首轮从「一次成稿」改为「工具组合构建」

> 用户拍板：LLM 不再一次手写整份计划 JSON，而是通过一组工具逐步构建/更新
> draft。本文记录决策脉络（含与 OpenAI function-calling 指南的对照）、
> 两个前置地基（shot 引用 + probe 回填）、V10 实现与首跑数据。

---

## 一、决策脉络

1. **提议**：工具化更新 JSON——模型按意图调工具调整计划，防编造、
   减负担、即时反馈（OpenAI 指南背书）。
2. **对照分析**（含 D 盘 FireRed 源码验证）：FireRed 是「节点内嵌 LLM 判断
   + plan_timeline 固定代码组装」双层结构；我们 V9 已有修订轮 ops（工具
   更新的机制实体）。混合方案（首轮一次性 + 修订工具化）与全工具化各有
   代价：轮次膨胀 / 全局判断碎片化 vs 誊抄错误 / 反馈回路长。
3. **OpenAI 指南逐条对照**（developers.openai.ac.cn function-calling）：
   - 支持：「不要让模型填你已知的参数」（→ probe 回填）、strict 结构化
     输出（→ 我们的封闭 schema 等价物）；
   - 反对拆细：「合并总是按顺序调用的函数」、工具 <20、定义耗 token；
   - 画像：工具循环是过程的形态，strict 一次性输出是产物的形态。
4. **用户决策**：首轮也工具化（本篇）。混合方案保留为回退评估基线。

## 二、前置地基（同日落地，独立可用）

1. **shot 引用**（plan_schema + plan_compiler._resolve_shot_refs）：clips 允许
   `{"shot": N}` 引用 list_shots 的镜头（#01 起），编译器从内容卡取精确边界
   展开。校验：与 trim 互斥、编号范围（报实际镜头数）、无卡提示先
   analyze_media。时间戳誊抄（实测 #1 错误源）从结构上消失。
2. **probe 自动回填**（video_agent._autofill_probe）：submit 后宿主用真实
   探针覆盖模型手抄值（只 video 片段；静图本机会探成 0.04s 怪值故跳过）。
   probe_mismatch 交叉核验保留为纵深（replan 路径）。

## 三、V10 实现

### plan_tools.py（新增，~450 行）

- **draft 状态挂宿主**（模块级；RUN_LOCK 串行保证单 run）：重试不重置——
  模型只修出问题的部分再 submit。
- **17 个工具**：new_plan / add_clips（批量，shot 引用优先，kind 自动判定，
  probe 一律剥离由宿主回填）/ set_clip / set_effect（同名覆盖=改参数，
  补上实测缺口）/ remove_effect / remove_clip（连带清挂载 overlay）/
  move_clip / set_transition（type=none 硬切）/ set_audio / clear_audio /
  add_text / remove_overlay / set_narration / set_captions / get_plan /
  validate_plan / submit。
- **每个工具返回**：操作结果 + draft 紧凑摘要（片段表/时长/校验状态），
  错误就地返回——反馈回路缩到单步。
- **校验两层**：单步（add_clips 逐项用合成单片段计划跑 plan_schema，零规则
  重复）；全量（validate_plan/submit，且用 **shot 解析副本**——未解析的
  shot 引用让 clip_duration 取不到时长，转场/overlay 规则会漏放，测试抓到）。

### 集成（video_agent.py）

- plan_with_retry 首轮（非 ops_mode）：`reset_draft()` 一次；invoke 后
  `take_submitted()` 优先、`extract_plan`（submit_plan legacy）兜底；
  probe 回填共用。
- 重试反馈 tool_mode 措辞：修工具 → 再 submit，不要 new_plan 重建。
- 工具注册：+17（总 25，超指南软上限——工具文档即提示词，可接受）。

### 提示词

- Workflow 第 6 步改为工具构建序列；Plan schema 段降位为「draft 数据形状
  参考」；select/workflow 宏标注仍走 submit_plan legacy。
- COMMON_STEPS 第 6/7 步：set_audio（snap_beats 参数）/ 完整工具序列
  （new_plan → add_clips(shot) → set_transition → set_audio →
  set_narration → validate_plan → submit）。

## 九、瓶颈 1 当晚修复：流式 + 首 token 超时（L1/L2/L3）

第七节定性为「LLM 请求无客户端级超时」——**复核代码后纠正：超时一直都在**
（10-11 上线，model.py MODEL_TIMEOUT=180），实测 541.6s ≈ 3×180 的真面目是
**openai SDK 超时后静默重试 2 次、每次重新挂满 180s**，逻辑调用层面无约束；
VLM 路径同机制（362s ≈ 3×120）。非流式 read timeout 必须 ≥ 整段生成时长
（合法大工具轮 30~80s），timeout 不敢压小，挂死请求只能陪挂满——这是结构性
冲突，收紧参数解决不了。

### 改动（model.py / server.py / app.js / .env.example + 测试）

1. **L2 核心**：默认流式 HTTP（MODEL_STREAMING=1）。流式下 read timeout 按
   chunk 间隔计——挂死在首 token 前后 ~60s 即断，健康慢生成不受整段预算
   约束，timeout 才敢压到 60。langchain-core 1.6.1 的 _should_stream 本就
   按实例属性把 .invoke() 路由到 _stream，但该路径不转发 run_manager；
   StreamingChatOpenAI 子类（_generate 聚合 + _stream 首 chunk hook）保证
   任何版本/路径下行为一致。
2. **L1 收紧**：MODEL_RETRIES 2→1、VLM_TIMEOUT/VLM_RETRIES 同步（60/1，
   env 可调）。最坏逻辑调用从 ~542s 压到 ~125s（2×60+退避）。
3. **补洞**：DEEPAGENT_MODEL 显式路径的 init_chat_model 此前完全没传
   timeout/max_retries，现已转发（显式路径不启用流式，供应商异构）。
4. **L3 可观测**：_stream 首 chunk → 模块 hook → server emit
   `llm_first_token`（plan_with_retry 期注册、finally 注销）→ 前端等待条
   区分「模型响应中」与「模型生成中（token 持续到达）」。
5. 回滚杆：MODEL_STREAMING=0 一键回非流式（timeout 默认值自动回 180/120）。

### 验证

- tests/test_model_streaming_timeout.py 7 项：默认值/回滚/env 覆盖/
  init_chat_model 补洞/挂死 stub（2s 预算内断、重试放大 ~2×2s）/
  SSE stub（.invoke() 流式聚合 content+tool_calls 与整段等价，回滚分支同测）/
