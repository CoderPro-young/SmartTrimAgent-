# 开发纪要 2026-10-28：V10 计划工具化——首轮从「一次成稿」改为「工具组合构建」

> 用户拍板：LLM 不再一次手写整份计划 JSON，而是通过一组工具逐步构建/更新
> draft。本文记录决策脉络（含与 OpenAI function-calling 指南的对照）、
> 两个前置地基（shot 引用 + probe 回填）、V10 实现与首跑数据。

---

## 一、决策脉络

1. **提议**：工具化更新 JSON——模型按意图调工具调整计划，防编造、
   减负担、即时反馈（OpenAI 指南背书）。
2. **对照分析**（含 D 盘 FireRed 源码验证）：FireRed 是「节点内嵌 LLM 判断
   + plan_timeline 固定代码组装」双层结构；我们 V9 已有修订轮 ops（工具
   更新的机制实体）。混合方案（首轮一次性 + 修订工具化）与全工具化各有
   代价：轮次膨胀 / 全局判断碎片化 vs 誊抄错误 / 反馈回路长。
3. **OpenAI 指南逐条对照**（developers.openai.ac.cn function-calling）：
   - 支持：「不要让模型填你已知的参数」（→ probe 回填）、strict 结构化
     输出（→ 我们的封闭 schema 等价物）；
   - 反对拆细：「合并总是按顺序调用的函数」、工具 <20、定义耗 token；
   - 画像：工具循环是过程的形态，strict 一次性输出是产物的形态。
4. **用户决策**：首轮也工具化（本篇）。混合方案保留为回退评估基线。

## 二、前置地基（同日落地，独立可用）

1. **shot 引用**（plan_schema + plan_compiler._resolve_shot_refs）：clips 允许
   `{"shot": N}` 引用 list_shots 的镜头（#01 起），编译器从内容卡取精确边界
   展开。校验：与 trim 互斥、编号范围（报实际镜头数）、无卡提示先
   analyze_media。时间戳誊抄（实测 #1 错误源）从结构上消失。
2. **probe 自动回填**（video_agent._autofill_probe）：submit 后宿主用真实
   探针覆盖模型手抄值（只 video 片段；静图本机会探成 0.04s 怪值故跳过）。
   probe_mismatch 交叉核验保留为纵深（replan 路径）。

## 三、V10 实现

### plan_tools.py（新增，~450 行）

- **draft 状态挂宿主**（模块级；RUN_LOCK 串行保证单 run）：重试不重置——
  模型只修出问题的部分再 submit。
- **17 个工具**：new_plan / add_clips（批量，shot 引用优先，kind 自动判定，
  probe 一律剥离由宿主回填）/ set_clip / set_effect（同名覆盖=改参数，
  补上实测缺口）/ remove_effect / remove_clip（连带清挂载 overlay）/
  move_clip / set_transition（type=none 硬切）/ set_audio / clear_audio /
  add_text / remove_overlay / set_narration / set_captions / get_plan /
  validate_plan / submit。
- **每个工具返回**：操作结果 + draft 紧凑摘要（片段表/时长/校验状态），
  错误就地返回——反馈回路缩到单步。
- **校验两层**：单步（add_clips 逐项用合成单片段计划跑 plan_schema，零规则
  重复）；全量（validate_plan/submit，且用 **shot 解析副本**——未解析的
  shot 引用让 clip_duration 取不到时长，转场/overlay 规则会漏放，测试抓到）。

### 集成（video_agent.py）

- plan_with_retry 首轮（非 ops_mode）：`reset_draft()` 一次；invoke 后
  `take_submitted()` 优先、`extract_plan`（submit_plan legacy）兜底；
  probe 回填共用。
- 重试反馈 tool_mode 措辞：修工具 → 再 submit，不要 new_plan 重建。
- 工具注册：+17（总 25，超指南软上限——工具文档即提示词，可接受）。

### 提示词

- Workflow 第 6 步改为工具构建序列；Plan schema 段降位为「draft 数据形状
  参考」；select/workflow 宏标注仍走 submit_plan legacy。
- COMMON_STEPS 第 6/7 步：set_audio（snap_beats 参数）/ 完整工具序列
  （new_plan → add_clips(shot) → set_transition → set_audio →
  set_narration → validate_plan → submit）。

## 四、测试与首跑

- `tests/test_v10_plan_tools.py` 8 项全过；全量回归 22 个文件全绿。
- **e2e（simtest8，真实素材+Flash）**：草原竖屏短片任务。工具轨迹
  `ls → probe×3 → list_shots → list_music → new_plan → add_clips →
  remove_clip×3 + add_clips（为凑 30s 预算调整图片时长——draft 迭代，
  一次性路径做不到的能力）→ set_transition×5 + set_audio →
  set_narration×2（自纠错文案笔误）→ validate_plan → submit`；
  **16 轮工具调用，计划零校验错误一次通过编译**（唯一 error 是 provider
  瞬时 400，被重试闭环吸收），27.75s 成片回验通过。probe 回填 2/2 视频
  片段、shot 引用 2 个视频片段（图片走 duration——混合使用符合设计）。
- 对照：submit_plan 路径同规模任务 3-6 轮。工具路径轮次多、但把
  「验证失败→整份重写」的循环换成了「构建中随时自查」。

## 六、持续对话压测（V10 后多轮实测，2026-10-28 下午）

三个会话 11 轮（simtest9 创作→修订→问答→撞缺口→重建→要方案；
simtest10 创作→混合修订→重启→接续；simtest11 创作→撞缺口→重启→接续）。

### 表现良好的部分

- **工具构建稳定**：simtest9 轮 1（44.5s 旅行短片）与 simtest11 轮 1
  （14.4s 快剪）均一次通过，模型提交前主动 get_plan 复查；
- **修订轮 ops** 正常（删片段+挪顺序），撞 overlay 越界时 R5 例外出口
  正确触发（submit_plan 修 overlay 完成）；
- **状态问答**：BGM 行/_preview 后缀/零 LLM 直答全对；
- **proposal 车道**：host 禁执行指令生效，4 方案零渲染；
- **ops 缺口提问**：三轮「加标题/加字幕」都正确识别并 ask_user。

### 抓到并修复的两个缺陷（均带回归测试）

**R9 · 问答接续无锚定**（simtest10 重启后接续，重度事故）：用户答
「重写计划补字幕」，`build_answer_brief` 只含问题+回答（V9 时代遗留，
无基线计划/素材约束/原任务），模型把整个素材池当新任务——**换素材**
（草原→演唱会）重建 9 片段 34s。修复：brief 附会话基线（原任务/
当前成片/片段表/BGM/素材清单 + 硬约束「不得换素材、不得重建作品，
重写以片段表为底稿」），server 传入 last_plan 等上下文；措辞同步
V10（ops 优先/submit_plan 例外）。simtest11 复测：同素材同结构仅加
「未完待续」overlay 于结尾片段。t18 回归。

**R10 · 防覆盖历史盲区**（simtest9 轮 4b）：守卫只比「上一版」产物名，
模型把输出名改回初版名 → 初版成片被静默覆盖。修复：`_guard_overwrite`
比对范围扩到会话 history 全部产物名（含 _preview 口径归一），
plan_with_retry 新增 history_outputs，server 传 session.history。
simtest11 复测输出正确改名 -r2。t17 扩展回归。

### 观察项（不修）

- 重建路径耗时偏长（simtest11 r2 服务端跑满 7 分钟+，客户端断连后
  管线继续完成——行为符合设计但等待体验差，节流/提速待阶段 2 评估）；
- 修订轮 ops 词表缺口（overlay/效果参数）在本轮被三次触发——阶段 2
  修订轮统一用 draft 工具（last_plan 载入初态）后自然消失，优先级升高。

## 七、晚间链路实测（sim-1028-v10a，同素材一键成片→多轮自然语言修订）

服务存活状态下新会话五连发（preview），TMP/_timed_run.py 外壳计时（事件到达
时刻，服务端不改）。总计 1092s ≈ 18 分钟，成片 2 版均 verify 通过。

### 各轮结果

| 轮 | 指令 | 耗时 | 结果 |
|---|---|---|---|
| 1 | 一键成片（72s 草原旅行 vlog） | **716.5s** | 成功；LLM 请求挂死超时重试耗掉 541s（75%） |
| 2 | 换抒情 BGM | 31.6s | **失败**：存量 overlay 越界 ×6，熔断正确停止 |
| 3 | 开头加大标题 3 秒 | 75.8s | 正确 ask_user（ops 词表缺口），单次 LLM 71s |
| 3b | 答「就用方案1」 | 268.3s | 成功：execute 车道做标题图插入 + submit_plan 重交，成片 74.95s，防覆盖改名 -r2 |
| 4 | 问 BGM/片段数 | **0.0s** | 零 LLM 直答命中（时长口径 71.5s 与成片 74.95s 不符，小瑕疵） |

### 抓到的结构性缺陷：last_plan 展开版不可重编译（R11 候选）

轮 2 失败根因坐实（对比三轮 plan 事件+会话文件）：

- 首轮 submit 的计划 overlays=0（旁白走 set_narration）；**last_plan 存的
  是编译器展开版**：narration→10 条 overlay 字幕、audio 带 original:"mute"
  内部字段、clips 被 trim/probe 展开（无 clip_duration/start）。
- 展开时 overlay duration 按旁白朗读时长取（4.91s），可超目标片段长
  （c1=3.5s）；渲染端宽松裁剪所以首轮播放正常，**修订轮把展开版载入重过
  严格校验必炸**——「换 BGM」这种最轻的修订被打挂。
- 下午 simtest9「撞 overlay 越界」应同根因（当时 R5 例外出口救场）。
- 修复方向：last_plan 双存 raw+expanded，修订轮载入 raw；或校验对编译器
  自产 overlay 放宽到与渲染端 min 裁剪同语义。优先级高。

### 耗时瓶颈定量（LangSmith，07:50 前后窗口 78 万 prompt / 2.6 万 completion tokens）

1. **LLM 单请求挂死是最大单点**：轮 1 第 3 个请求 OpenAITimeoutError 挂
   542s 才失败（无请求级超时保护），重试闭环吸收后 128s 走完 14 轮工具
   链一次通过编译。客户端超时 + 快速重试可把最坏路径从 12 分钟压回 3 分钟内。
2. **DeepSeek-V4-Flash 输出速度 17~36 tok/s**：大 completion 轮次线性变慢
   ——add_clips/set_transition 批量调用（2500+ tok）30~80s；ask_user 长思考
   71s。V10 工具化的轮次代价主要落在 completion 体积上。
3. **上下文每轮全量重发**：工具循环内 prompt 13.7k→38k 累积；15~38k prompt
   本身处理不慢（1~11s），暂非瓶颈，量级再涨可做旧轮结果摘要。
4. 渲染/分析都不是瓶颈：preview 72s 成片渲染 5~41s；素材分析缓存命中 5.6s
   （12 素材 47 镜头），新图冷分析约 3s/张。

### 防线确认（本轮全部按设计触发）

超时重试闭环（轮1）、同错熔断（轮2）、ops 缺口 ask_user（轮3）、R9 接续
锚定（3b 未换素材未重建）、R10 防覆盖改名 -r2、plan_diff global touched=2/12。

## 八、R11 修复落地：计划双存（raw + expanded）

第七节的「last_plan 展开版不可重编译」当晚修复，用户拍板方案后实施。

### 改动（4 文件 + 测试）

1. **plan_compiler**：`CompileResult` 增加 `raw_plan`（validate 通过后、
   `_expand_plan` 前 deepcopy）；旁白/文案 4 处铺轴 overlay 打 `_src`
   内部标记（narration/captions）。
2. **plan_schema**：`_src` 进 OVERLAY_TEXT_KEYS 白名单；overlay 越界规则
   豁免带标字幕——「片段内装得下」只约束模型手写（防时间戳誊抄错），
   编译器自产跨片字幕按绝对时间轴渲染是设计语义。
3. **server**：`_commit_compiled` 存档改存 `raw_plan`（getattr 兜底）；
   `plan_diff` 改 raw vs raw 同空间比较（消展开产物假 diff）。
   apply_ops 底稿 / 修订 brief 片段表 / status_answer 随 last_plan 自动切 raw。
4. **intent**：status_answer 时长口径改走 `clip_duration`（图片 duration
   此前没被累计——轮 4 报 71.5s 实际 74.95s 的根因，顺手修复）。

### 豁免的第二入口

`/api/replan`（前端卡片回改）提交的是展开版（exec_plan 事件负载），首轮带
旁白时同样撞越界——`_src` 豁免同时护住该路径，无需前端改动。

### 验证

- **tests/test_v11_raw_archive.py 4 项**：raw 留存/分离、**轮 2 事故直接
  复现**（raw + 换 BGM 重编译通过且字幕逐字一致）、豁免只认带标
  （无标越界照拦）、status_answer 口径；全量 23 测试文件全绿。
- **端到端（sim-1028-v11a，真实 13 素材）**：一键成片《草原一路向北》
  94.03s（1101.6s，其中素材被挪动后内容卡冷缓存全量重分析 944s——
  拷贝改 mtime 即失效，观察项）；同会话「换抒情钢琴 BGM」**13.8s 出片
  -r2**，plan_diff touched=0/14、防覆盖改名、verify 全部正常。
  修复前同场景 31.6s 熔断失败零产物。
- 期间 provider 再次并发超时 362s×4（重试闭环吸收），超时无请求级
  保护仍是最大单点（第七节瓶颈 1 不变）。

### 遗留

- 旧会话文件（无 raw_plan 时代存档的展开版 last_plan）不迁移，读到照旧
  （可能熔断）；新会话起全走 raw。
- 内容卡缓存对文件 mtime 敏感——素材挪动/重新放置即全量重分析，可考虑
  按 content hash 键控（观察项，未修）。
- 阶段 2「修订轮统一 draft 工具」现在有了干净前提：draft 初态直接载入
  raw_plan。
