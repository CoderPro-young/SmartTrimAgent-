一、产品演进：三个台阶

✅ 关键定性（第三方分析）：此前 AI 负责执行（"删掉第几秒""加个转场"），创作者主导流程； 之后 AI 开始承担从素材理解、内容整理、粗剪、包装到成片的大量执行，工具角色 从"操作翻译器"变成"意图实现者"。

二、架构三层

2.1 多 Agent 分治 + Skill 化调度

✅ 公开披露的机制：主 Agent 理解意图 → 分发给剪辑 / 配乐 / 调色等领域"专家"子 Agent → 子 Agent 精准调用对应 Skill → 把"把视频调得亮一点"映射到具体的亮度参数轨道。

✅ 极客公园的定性（值得记）：市面上能做到"视频生成 + 专业编辑 + Skill 化执行"三位一体的 只有剪映。壁垒不是大模型，而是多年积累的海量功能与底层编辑引擎。 这句话很关键——它说明 Skill 化的前提是"有足够多的能力可供封装"。

2.2 动态草稿协议（最核心的设计）

✅ 公开披露：AI 不是吐一个改不了的成品视频，而是直接在用户的剪辑轨道/草稿上操作， 端云协同、每一步实时同步、可见可回退可微调。

🔶 工程实质：AI 产出的不是视频文件，而是"对草稿对象模型的一组修改"。 这带来三个直接好处：

  1. LLM 的不确定性被隔离在"生成初稿"这一步，后续迭代交给确定性系统和人
  2. 每步可 undo，错误成本低
  3. 产物是"活的工程"，用户能继续手动精修

✅ 佐证：另一篇实测提到，AI 文字成片的产物可一键拆分成画面 / 口播 / 配乐 / 字幕四个多轨道 再精修——"生成的结束只是工作的开始"这个理念被工程化了。

2.3 反思与反问

✅ 指令模糊或执行失败时主动确认需求，而不是强行乱做。 🔶 这等价于"程序化 self-correction"：把不确定性交回给用户而不是硬猜。

三、Skill 机制详解

3.1 Skill 是什么

🔶 推断：一个 Skill = 参数 schema + 到轨道操作的映射。 比如"调亮一点" → {skill: "brightness", args: {value: +0.1, target: "clip_3"}}。

它和"让 LLM 直接写时间线数据"的本质区别：LLM 不碰底层数据结构，只填参数。

3.2 Skill 清单（官方界面抓取）

人声分离 / 图片 AI 消除 / 视频字幕 AI 擦除 / 音乐生成 / 一键美颜 / 人脸马赛克 / 智能包装 / 字幕批量改词 / 曲线变速 / 删除指定词 / AI 转场（一镜到底等）/ 视频生成 / 改词翻唱 / 音频翻译 / 声音分离 / 数字人……

⚠️ 注意：人脸马赛克、智能包装、删除指定词（≈剪口播）与 SmartTrimAgent 的能力面直接重合。 区别只在产物形态——剪映的 Skill 跑在 GUI 轨道上（可手动续改）， 我们跑在 ffmpeg 流水线上（可程序化回验）。

3.3 三类用户分层（官方定位）

用户需求心理匹配能力
剪辑高手"我知道怎么做，但我懒得做"批量编辑 Skill，多轨道大批量处理
剪辑初阶"我不会做，你来帮我想"模糊指令触发基础 Skill
剪辑小白零思路零操作生成式 Skill 一键出片

🔶 这个分层解释了他们为什么把"批量操作"放在第一位—— 最大的用户群（初阶 + 小白）要的不是创意，是把脏活干掉。

四、架构范式分析：命令式 vs 声明式（重点）

这是剪映与 SmartTrimAgent 最本质的分岔，也是解释它那些实测缺陷的关键。

4.1 两条链路对比

剪映：命令式（imperative）增量

对话指令（每轮一句）
   → 主 Agent 理解 + 分发
   → 剪辑/配乐/字幕… 子 Agent 各领一条
   → Skill = 参数化命令（"调亮" → 亮度轨道参数）
   → 直接写草稿轨道（每步可 undo、可手动续改）
   → 用户手动导出

SmartTrimAgent：声明式（declarative）全量

自然语言需求（一次全量）
   → Planner（LLM）产出编辑计划 JSON
   → plan_compiler 统一校验 + 时间轴推导
   → ffmpeg 执行 + ffprobe 回验
   → 成品 + 检视面板可回改

4.2 三个关键差异

维度剪映（命令式）我们（声明式）
中间产物一串命令/操作一份完整的计划 JSON
校验时机逐条执行，无全局合成层编译器对整体统一校验
产物形态活草稿（GUI 生态）渲染成品 + 程序化回验（自动化场景）

4.3 用实测缺陷反证架构

✅ 36氪实测："把第三段速度调慢，同时降低这段背景音乐音量，再加个电影感字幕" ——它往往只执行了其中一到两个要求，或者执行顺序出错。

🔶 这个缺陷不是执行质量问题，是架构的必然结果： 命令式架构下，三个要求被拆给三个子 Agent 各自执行， 没有一个人负责检查"三件事是否都做了"。漏了也没人发现。

✅ 同一篇实测还记录："系统不会主动提示你哪里没配好，必须自己从头到尾检查一遍" ——"生成快、审核慢"，效率优势被抵消。

而我们的架构天然免疫第一个问题：三项指令都进同一个 plan JSON， 编译器校验时"第 2 项参数越界"是显式报错，缺哪项、错哪项一目了然。 这不是运气差异，是架构保证的差异。

4.4 但要承认它的优势

动态草稿协议在我们的架构里确实更难做——因为我们没有"一个持续存在的草稿对象"。 我们的对应替代是 P0-2 参数卡片回改（改 plan → 重新编译，不回 LLM）， 形态上更笨，但保留了核心价值：把 LLM 隔离在生成初稿这一步。

七、对 SmartTrimAgent 的启示

  1. 能力面重合度超预期：人脸马赛克、剪口播、字幕、转场、配乐——双方瞄准同一批需求。

我们的差异化只剩两条路：产物可程序化回验（质量门禁） 与 流水线透明（检视面板）。 这两条恰好是剪映实测被诟病的地方，应优先做深而不是做宽。

  1. Skill 注册表是同构思路：剪映 Skill = 参数 schema + 执行映射 + 用户可见的说明书。

我们的 skills.py 已实现这个最小版本（roadmap T1，已完成）。

  1. 动态草稿协议的工程实质 = "AI 只产初稿 + 确定性系统承接迭代"：

我们的 P0-2（参数卡片回改）就是它的最小实现。

  1. 组合指令不全要反过来做：把"漏执行"变成"显式报错"。

这正是 2026-09-16 实测发现的缺陷（clip 未知字段被静默忽略）要修的方向。

  1. 别在"创意"上跟它比：它有 10 亿用户、Seedance 底模、海量模板，也只做到"模板感很重"

（36氪 68 分）。这反过来验证了"只做 0→60 分"的定位是理性的。
